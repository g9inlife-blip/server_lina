# Runtime Protocol

## 역할 분리
사용자는 **최종 게임 화면/동작을 확인하는 검증자**다. Codex는 APK 빌드부터 에뮬레이터 조작, ADB, logcat, 프로세스/Activity 조작, 상태 수집까지 실행 환경의 기술 작업을 담당한다.

## 절대 원칙: 사용자에게 ADB 작업을 요청하지 않는다
사용자에게 `adb`, `adb shell`, `adb logcat`, APK 설치/삭제, 앱 데이터 초기화, Activity/프로세스 조작, 네트워크 on/off, 스크린샷 추출, 로그 수집 등 터미널/에뮬레이터 명령을 직접 실행하게 하지 않는다. 필요한 모든 기술 작업은 Codex가 로컬 환경에서 수행한다.

## 기본 진행 방식: Codex 선행 → 사용자 확인 → 다음 단계
에뮬레이터 상태나 런타임 동작을 확인할 때는 다음 순서를 따른다.

### 1. Codex 선행 작업
Codex가 필요한 범위에서 자동으로 수행한다.
- patched APK 빌드/서명/설치
- 필요 시 앱 데이터 초기화
- 앱 실행/재실행
- ADB 조작
- logcat 수집/분석
- 프로세스/Activity 상태 확인
- 필요 시 네트워크 상태 변경
- crash/ANR/예외 확인
- 스크린샷 및 런타임 증거 수집

### 2. Codex가 사용자 확인 요청
Codex가 기술 로그를 먼저 확인한 뒤, 사용자에게는 화면에서 확인 가능한 항목만 요청한다.

예:
```text
[RUN-001 사용자 확인 요청]
에뮬레이터의 현재 화면을 확인해 주세요.

체크:
1. 업데이트 실패 화면이 나타나는가? (예/아니오)
2. 메인 화면까지 진입하는가? (예/아니오)
3. 화면에 표시된 주요 문구는 무엇인가?
4. 버튼을 눌렀을 때 반응하는가? (예/아니오)

확인 후 결과를 알려주세요.
```

사용자에게 로그 분석이나 ADB 명령 실행을 요청하지 않는다.

### 3. 사용자는 화면 상태만 응답
예:
- "업데이트 실패는 안 뜨고 메인 화면까지 들어갔어."
- "메인 화면은 떴는데 로딩에서 멈췄어."
- "버튼을 눌러도 아무 반응이 없어."

### 4. 결과 판정 후 다음 단계
사용자 응답을 현재 가설/자동 로그와 비교한다.
- 성공 조건 충족 → 다음 테스트/분석
- 예상과 다른 상태 → Codex가 필요한 ADB/logcat/Ghidra 추가 조사
- 원인 불명 → Codex가 증거 수집 후 다시 사용자 확인 요청

특히 화면 전환, 초기화 결과, 업데이트 우회 여부, 저장 데이터 영향처럼 실제 게임 상태가 중요한 검증은 **사용자 확인을 기준점으로 삼고, 확인 응답 후 다음 단계로 진행한다.**

## Codex 자동 검증과 사용자 검증의 구분
### Codex가 판단
- 빌드/서명/설치 성공 여부
- 프로세스/Activity 실행 여부
- crash/ANR/native crash
- logcat 예외/stack trace
- 네트워크 요청/실패 흔적
- 파일 생성/변경
- 패치 opcode/바이트 적용 여부

### 사용자가 판단
- 실제 화면에 무엇이 보이는지
- 메인 화면 진입 여부
- 업데이트 화면이 사라졌는지
- 버튼/터치 반응
- 게임 진행 가능 지점
- 화면이 멈췄는지/계속 진행되는지
- 최종 체감 동작

## 단계별 확인 원칙
한 번의 테스트에서 너무 많은 것을 동시에 검증하지 않는다.

```text
Codex: APK 패치/빌드/설치/실행
  ↓
Codex: logcat/프로세스 상태 자동 확인
  ↓
Codex: 사용자에게 화면 체크 요청
  ↓
사용자: 확인 결과 응답
  ↓
GPT/Codex: 결과 판정
  ↓
필요 시 Codex가 추가 ADB/logcat/Ghidra 조사
  ↓
다음 사용자 확인 요청 또는 다음 단계
```

## 사용자에게 전달할 정보
가능한 한 다음 3가지만 전달한다.
1. 어떤 화면/상태를 확인할지
2. 무엇을 체크할지
3. 결과를 어떻게 답하면 되는지

ADB 명령, logcat 명령, 내부 주소, opcode 등 기술 세부사항은 Codex/GPT의 작업 기록으로 남긴다.

## 런타임 기록
각 테스트는 `research/runtime/` 또는 해당 PATCH 결과 문서에 기록한다.

```text
RUN-001
PATCH: PATCH-001
APK: <build id 또는 sha256>

Codex 자동 확인:
- 빌드: PASS/FAIL
- 서명: PASS/FAIL
- 설치: PASS/FAIL
- 실행: PASS/FAIL
- 프로세스: PASS/FAIL
- crash/ANR: 없음/있음
- logcat: <핵심 결과>
- 네트워크 오류: 없음/있음/확인 필요

사용자 확인 요청:
1. 업데이트 실패 화면: 예/아니오
2. 메인 화면 진입: 예/아니오
3. 현재 화면 문구: <사용자 응답>
4. 터치 반응: 예/아니오

사용자 응답:
<원문 또는 요약>

판정:
PASS / FAIL / NEED_MORE_INVESTIGATION

다음 단계:
<다음 TASK 또는 추가 런타임 확인>
```

## 원칙
런타임 결과는 정적 분석보다 우선한다. 다만 한 번의 실행 결과만으로 원인을 단정하지 않는다. Codex는 기술적 증거를 수집하고 사용자는 실제 화면 상태를 확인한다. 두 결과를 종합해 다음 단계를 결정한다.
