- 33B 구조 (PCAP 차용):
  ```
  0x00-0x07: zeros
  0x08: 0x01
  0x09-0x10: session ID (8B)
  0x11-0x18: ??? (8B)
  0x19-0x20: server public (8B)
  ```

### 16:50 - 복호화 시도 (실패)
- 221B 구조:
  ```
  0x00-0x07: session ID (우리 33B와 일치!)
  0x08-0x0B: 51000001
  0x0C-0x0F: 변경값 (타임스탬프?)
  0x10-0x17: zeros
  0x18-0x1B: c1000000
  0x1C-0x1F: 세션별 변경값
  0x20~: 189B 데이터
  ```
- 189B는 AES 블록(16B)의 배수가 아님
- AES-128-CBC, IV=zeros로 복호화 시도 → 실패

### 17:05 - 33B 버그 발견 및 수정

- 키 유도 방식도 Handshake2 확인: `LE64(s1) || LE64(s2)`

## 핵심 교훈

1. **51B는 PCAP에 없음**: 실제 서버는 368B만 사용. 51B는 로컬에서만 나오는 프로토콜
2. **33B 형식 미검증**: PCAP의 33B를 차용했지만 51B용인지는 불명
3. **복호화 성급**: 189B가 AES 블록 배수가 아닌데도 복호화 시도
4. **False positive 주의**: PKCS7 패딩만으로 성공 판정하면 안 됨
5. **구조 분석 우선**: 암호화 영역의 정확한 offset/length를 먼저 확정해야 함
