# 코드데이터 역매핑 분석 트랙 — GPT 자문

**작성일**: 2026-10-02  
**목적**: 서버 구현 트랙과 분리하여 Item / Hero / Weapon / Equipment 등 게임 코드데이터의 protobuf ↔ 런타임 객체 ↔ UI 연결관계를 역분석한다.

## 1. 분석 트랙 분리

현재 서버 트랙은 Bootstrap Replay + Surgical Patch까지 성공했으므로 서버 구현은 별도 진행한다.

이 문서는 다음 분석만 담당한다.
- Bootstrap protobuf의 데이터 필드 구조
- OpInfo 각 데이터 객체와 protobuf field의 대응관계
- Ghidra에서 Proto 계열 클래스/함수의 생성·병합·저장 흐름
- Frida 런타임에서 실제 객체와 UI 전달 흐름
- Surgical Patch를 이용한 의미 검증

분석 대상 우선순위:
1. Currency
2. Item
3. Hero
4. Weapon
5. Equipment
6. Chapter
7. Team / Quest / 기타

## 2. 현재 확정된 기준선

### 2.1 네트워크/Bootstrap

운영 Bootstrap Replay로 실제 Main 화면 진입에 성공했다.
또한 실측 Bootstrap의 특정 protobuf 값만 변경하는 Surgical Patch가 성공했다.

대표 사례:
- field 38의 currency entry
- currency ID 43000001
- amount 35025 → 999999
- 실제 게임 UI에서 999,999 표시 확인

따라서 현재는 protobuf를 처음부터 Builder로 만들 필요 없이, 실측 응답을 분석용 기준 데이터로 사용한다.

### 2.2 OpInfo

런타임에서 확인된 주요 필드:
- User +0x88
- Heros +0x90
- Items +0x98
- Weapons +0xA0
- Equiments +0xA8
- Mails +0xB0
- Olds +0xB8
- Chapters +0xC0
- Sections +0xC8
- Teams +0xD0
- ViewItems +0xD8
- Fashions +0xE0
- Quests +0xE8
- Shops +0xF0
- Charges +0xF8
- Friends +0x100
- Exam +0x108
- Rival +0x110
- Ranks +0x118
- Activities +0x120

주의: 위 값은 C# 객체 메모리 오프셋이며 protobuf field 번호가 아니다.

## 3. 현재 Bootstrap protobuf에서 확인된 최상위 field

실측 Bootstrap에는 다음 field들이 존재한다.

1, 2, 4, 5, 12, 13, 14, 15, 21, 35, 37, 38, 39, 40, 43, 44, 45, 48, 49, 51, 56

| protobuf field | 런타임 의미 | 근거 | 상태 |
|---|---|---|---|
| 21 | Items | 276개 entry, 각 entry {f1=ID, f2=count}, OpInfo.Items 경로와 일치 | 확정 수준 |
| 35 | User | UserID/username을 포함한 User 구조 | 확정 |
| 38 | Currency | 35개 currency entry, Gold ID 43000001의 amount 변경이 실제 UI에 반영 | 실증 확정 |
| 43 | Chapters | 61개 entry, Chapter 런타임 구조와 대응 | 확정 수준 |
| 37/39/40/44/45/48/49/51/56 | 미확정 | 구조 분석 필요 | 미확정 |

## 4. 분석 방법

단일 근거로 field 의미를 결정하지 않는다.
각 데이터는 protobuf, Ghidra, Runtime 세 방향을 교차검증한다.

protobuf → field / nested field / ID / count / value

Ghidra → Proto 클래스 / Deserialize / Merge / Dictionary / List / cache

Runtime → OpInfo 객체 → DataCenter → UI

A + B + C가 일치하면 확정, A만 일치하면 추정으로 기록한다.

## 5. Item 분석

현재 가장 좋은 출발점이다.

### 5.1 알려진 구조

Bootstrap field 21
- repeated bytes × 276
- 각 entry: field 1 = Item ID, field 2 = Count

### 5.2 다음 목표

대표 Item 5~10개를 선정한다.
각 Item에 대해 protobuf의 Item ID/Count 기록 → 런타임 ProtoItem/object 변환 추적 → DataCenter.MergeItem 경로 확인 → Warehouse cache 저장 구조 확인 → Warehouse UI 표시 데이터 연결 → Count surgical patch로 UI 반영 여부 확인.

목표 경로:
field 21 → ProtoItem → OpInfo.Items → MergeItem → DataCenter cache → Warehouse → UI

## 6. Hero 분석

Item 다음으로 OpInfo.Heros를 직접 추적한다.
우선 Ghidra에서 다음 문자열/함수/타입을 검색한다.
OpInfo / Hero / ProtoHero / Heros / MergeHero / Dictionary / List

확인 대상:
- Hero 객체 생성 위치
- Deserialize 직후 Hero 데이터가 저장되는 함수
- OpInfo.Heros 대입 지점
- Hero ID
- Level
- Rank/rarity
- EXP
- 성장 관련 수치
- 장착 Weapon/Equipment와의 연결

protobuf field는 개수만 보고 추측하지 않는다.

## 7. Weapon / Equipment 분석

Hero 분석에서 확보한 ID와 연결관계를 이용한다.
우선순위: OpInfo.Weapons → ProtoWeapon, OpInfo.Equiments → ProtoEquipment/ProtoEquiment

특히 Equipment는 게임 내부 표기에서 Equiments로 되어 있을 가능성이 있으므로 Ghidra 검색 시 오탈자까지 그대로 사용한다.

## 8. Surgical Patch 실험 원칙

실험에서는 한 번에 한 값만 변경한다.
좋은 실험: 원본 Item Count = 10, 패치 Item Count = 999, 나머지 데이터는 원본 그대로.
나쁜 실험: Item + Hero + Weapon + gzip + KCP를 동시에 변경.

판정:
- UI 값 변경 → 데이터 의미 강하게 확정
- 런타임 객체 값 변경만 확인 → 구조 확정에 가까운 증거
- protobuf만 변경되고 UI 변화 없음 → 중간 변환/캐시/조건 확인
- TryRead 실패 → protobuf 구조 자체 또는 serialization 문제부터 재검증

## 9. Ghidra 분석 우선 검색어

ProtoItem, ProtoHero, ProtoWeapon, ProtoEquipment, ProtoEquiment, MergeItem, MergeHero, MergeWeapon, MergeEquipment, MergeEquiment, OpInfo, Heros, Items, Weapons, Equiments

함수명을 검색할 때는 프로젝트의 Ghidra 파일 그룹 규칙을 따른다.
파일 그룹은 namespace를 포함한 전체 함수명의 시작 2글자를 기준으로 한다. < > $는 _로 치환되어 있다.
예: Alioth.S1.Net.KCPTube$$TryRead → AL.txt

## 14. 2026-10-02 실제 Ghidra 처리경로 추적 결과

이번 단계에서는 계획 단계에 머물지 않고 Ghidra Listing의 실제 호출 관계를 추적했다.

### 14.1 DataCenter.ProccessRequestRes → 각 OpInfo 데이터의 직접 전달

확인 함수:

`DataCenter$$ProccessRequestRes @ 0x016e203c`

해당 함수의 실제 호출부에서 다음 관계가 확인된다.

```
OpInfo + 0xA0 (Weapons)
    ↓
DataCenter$$MergeWeapon @ 0x016e414c

OpInfo + 0xA8 (Equiments)
    ↓
DataCenter$$MergeEquip @ 0x016e4348

OpInfo + 0x98 (Items)
    ↓
DataCenter$$MergeItem @ 0x016e4700

OpInfo + 0x90 (Heros)
    ↓
DataCenter$$UpdateHeroInfo @ 0x016e4ba4
```

실제 Listing:

```
016e29dc  ldr x0,[x20, #0x40]
016e29e0  ldr x1,[x26, #0xa0]
016e29e4  bl 0x016e414c

016e29e8  ldr x0,[x20, #0x38]
016e29ec  ldr x1,[x26, #0xa8]
016e29f0  bl 0x016e4348

016e29f4  ldr x1,[x26, #0x98]
016e29f8  mov x0,x20
016e29fc  bl 0x016e4700

016e2a00  mov x0,x20
016e2a04  mov x1,x26
016e2a08  bl 0x016e4ba4
```

여기서 `x26`은 Response로부터 만들어진 OpInfo 객체이며, 기존 runtime 관측의 +0x90/+0x98/+0xA0/+0xA8과 정확히 연결된다.

따라서 다음은 더 이상 단순 추정이 아니다.

| Runtime OpInfo | 실제 처리 함수 | 상태 |
|---|---|---|
| +0x90 Heros | UpdateHeroInfo | **Ghidra 직접 확인** |
| +0x98 Items | MergeItem | **Ghidra 직접 확인** |
| +0xA0 Weapons | MergeWeapon | **Ghidra 직접 확인** |
| +0xA8 Equiments | MergeEquip | **Ghidra 직접 확인** |

### 14.2 Item 처리 경로

`DataCenter$$MergeItem @ 0x016e4700`

호출자는:

```
DataCenter$$ProccessRequestRes
    ↓
MergeItem(DataCenter, OpInfo.Items)
```

MergeItem 내부에서 확인된 주요 동작:

- `Dictionary<int, object>` 접근
- 기존 항목 `get_Item / set_Item`
- `Dictionary<Int32Enum, object>` 접근
- `DataManager$$TryGetBaseData`
- 기존 항목 제거 `Dictionary.Remove`
- enumerate를 통한 기존 cache와 신규 데이터 병합

즉 Item은 단순히 protobuf 목록을 UI에 직접 전달하는 것이 아니라:

```
OpInfo.Items
    ↓
DataCenter.MergeItem
    ↓
ID 기반 Dictionary cache
    ↓
BaseData 조회
    ↓
Warehouse/UI
```

형태로 정리된다.

### 14.3 Warehouse가 실제로 사용하는 DataCenter cache

`WareHousePanelMono$$RefreshWareHouse @ 0x0104c1f8`에서:

```
0104c234  ldr x8,[x22]
0104c238  ldr x8,[x8, #0xb8]
0104c23c  ldr x0,[x8, #0x90]
```

가 확인된다.

즉 Warehouse는 DataCenter singleton에서 특정 cache/object를 얻은 뒤 `InitData`/UI 갱신으로 연결한다.

`WareHousePanelMono$$InitData @ 0x0104ace0`에서는:

- `Dictionary<int, object>.Values`
- `Where`
- `OrderByDescending`
- `ToList`

가 확인된다.

따라서 Warehouse의 표시 목록은 **ID→객체 Dictionary의 Values를 필터/정렬하여 만든 List**라는 점이 정적 분석으로 확인됐다.

`WareHousePanelMono$$ShowGoods @ 0x0104d6e8`에서는 최종적으로:

```
List<object>
    ↓ ToArray
    ↓ LoopScrollRect.objectsToFill
    ↓ ClearCells
    ↓ RefillCells
```

로 UI에 공급된다.

### 14.4 Item UI가 참조하는 실제 코드데이터

`ItemShowNormalMono$$SetItem @ 0x00eb0ddc`에서 다음 호출들이 확인된다.

- `DataManager$$TryGetBaseData`
- `BaseData$$get_icon`
- `BaseData$$get_NameByWord`
- `BaseData$$get_type`
- `BaseData$$get_quality`
- `BaseData$$get_star`
- `BaseData$$get_specialShow`
- `AliothExtensions$$SetSprite`
- `AliothExtensions$$SetTextExt`

따라서 Item의 네트워크 ID가 UI에 도달하면 최종 표시명은 별도의 `Word` 데이터와 `BaseData`를 통해 해결된다.

이는 다음 구조를 지지한다.

```
network Item ID
    ↓
Item runtime object
    ↓
DataManager.GetBaseData(ID)
    ↓
BaseData
    ├─ icon
    ├─ quality
    ├─ type
    ├─ star
    └─ NameByWord
             ↓
        Word__krRecord
```

## 15. Unity 코드데이터의 암호화 해제와 네트워크 ID 실증

Unity 원본 `ItemRecord.json`에서 다음 데이터를 직접 확인했다.

첫 Item:

```
currentCryptoKey = 444444
hiddenValue      = 43444445
m_icon           = item_43000001
m_nameId         = 143000001
m_describeId     = 243000001
```

계산:

```
43444445 XOR 444444 = 43000001
```

두 번째/세 번째 Item도 동일하다.

```
43444446 XOR 444444 = 43000002
43444447 XOR 444444 = 43000003
```

따라서 Item의 `m_id`는 단순 저장값이 아니라:

```
network ID = hiddenValue XOR currentCryptoKey
```

형태로 복원되는 것으로 실증됐다.

이 결과는 사용자가 제시한 `currentCryptoKey + hiddenValue` 기반 코드 분석 방향과 일치한다.

### 15.1 Equipment에서도 동일한 규칙 확인

`EquipmentRecord.json` 첫 항목:

```
currentCryptoKey = 444444
hiddenValue      = 41374812
m_icon           = equip_41000000
m_nameId         = 141000000
```

계산:

```
41374812 XOR 444444 = 41000000
```

다음 항목:

```
41374813 XOR 444444 = 41000001
41374814 XOR 444444 = 41000002
```

즉 Equipment 네트워크 ID 계열은 `41xxxxxx`이며, Unity 정적 데이터의 ID와 직접 연결된다.

### 15.2 Weapon에서도 동일한 규칙 확인

`WeaponRecord.json` 첫 항목:

```
currentCryptoKey = 444444
hiddenValue      = 40145436
m_icon           = w_t_10000
m_nameId         = 140000000
m_code           = 10000
```

계산:

```
40145436 XOR 444444 = 40000000
```

다음 항목도:

```
40145437 XOR 444444 = 40000001
40145438 XOR 444444 = 40000002
```

따라서 Weapon 네트워크 ID 계열은 `40xxxxxx`이다.

## 16. 사용자가 제시한 1/2/3/4 접두어 규칙과의 실데이터 대조

현재 실제 Unity 원본에서 다음 대응이 확인된다.

### Item

```
network ID : 43000001

name       : 143000001
describe   : 243000001
```

### Equipment

```
network ID : 41000000

name       : 141000000
describe   : 0
```

### Weapon

```
network ID : 40000000

name       : 140000000
describe   : 0
```

즉:

```
네트워크 코드 = XXXXXXXXX
명칭 코드    = 1 + 네트워크 코드
설명 코드    = 2 + 네트워크 코드
```

라는 관계가 Item 데이터에서 직접 관측되고, Equipment/Weapon에서도 명칭 계열이 같은 방식으로 맞는다.

따라서 사용자가 제시한:

```
52000100
→ 152000100
→ 252000100
→ 352000100
→ 452000100 ...
```

규칙은 현재까지 확보한 실제 데이터와 **구조적으로 일치한다**.

단, `52000100` 자체의 실제 레코드와 3/4 계열 필드까지 직접 확인하기 전에는 해당 개별 코드에 대해 확정 판정을 내리지 않는다.

현재 판정:

- 접두어 기반 계열 규칙: **강한 실증**
- Item 43000001 → 143000001/243000001: **실증 확정**
- Equipment 41000000 → 141000000: **실증**
- Weapon 40000000 → 140000000: **실증**
- 52000100 개별 사례: **미확정**

## 17. Hero 분석 방향 수정

Hero는 `DataCenter$$MergeHero`라는 별도 함수가 존재하지 않는다.

현재 직접 확인된 진입점은:

```
DataCenter$$ProccessRequestRes
    ↓
DataCenter$$UpdateHeroInfo @ 0x016e4ba4
    ↓
HeroInfo$$InitHero @ 0x016e5fd4
    ↓
HeroInfo / DataManager / cache
```

UpdateHeroInfo에서 확인된 호출:

- `Dictionary<int, object>.TryGetValue`
- `HeroInfo$$InitHero`
- `HeroInfo$$FinalUpgradeHero`
- `DataManager$$TryGet<object>`
- `DataCenter$$ConfirmCallHero`
- HashSet<int> 관리
- Dictionary enumeration

따라서 Hero는 Item/Weapon/Equipment처럼 `MergeHero`를 찾는 방식이 아니라 **UpdateHeroInfo → InitHero**를 중심으로 추적해야 한다.

이것은 다음 분석에서 중요한 방향 수정이다.

## 18. 현재 코드데이터 역매핑 그래프

현재까지 확정/실증된 그래프:

```
Bootstrap protobuf
    │
    ├─ field 21
    │      ↓
    │   OpInfo.Items (+0x98)
    │      ↓
    │   DataCenter.MergeItem
    │      ↓
    │   Dictionary<int, object>
    │      ↓
    │   DataManager.TryGetBaseData
    │      ↓
    │   BaseData
    │      ↓
    │   Warehouse / Item UI
    │
    ├─ [Hero field 미확정]
    │      ↓
    │   OpInfo.Heros (+0x90)
    │      ↓
    │   DataCenter.UpdateHeroInfo
    │      ↓
    │   HeroInfo.InitHero
    │
    ├─ [Weapon field 미확정]
    │      ↓
    │   OpInfo.Weapons (+0xA0)
    │      ↓
    │   DataCenter.MergeWeapon
    │      ↓
    │   WeaponInfo.Refresh / WeaponInfo ctor
    │
    └─ [Equipment field 미확정]
           ↓
        OpInfo.Equiments (+0xA8)
           ↓
        DataCenter.MergeEquip
           ↓
        EquipInfo.Refresh / EquipInfo ctor
```

여기서 **protobuf field 번호 자체는 아직 Hero/Weapon/Equipment에 대해 확정하지 않는다.**

## 19. 다음 분석의 우선순위 변경

현재 가장 생산적인 순서는 다음과 같다.

### 1순위 — Item

Item은 이미:

- protobuf field 21
- 네트워크 ID
- currentCryptoKey XOR hiddenValue
- ItemRecord
- nameId/describeId
- DataCenter.MergeItem
- Warehouse cache
- Warehouse UI

까지 연결됐다.

다음 목표는 field 21의 실제 276개 ID를 ItemRecord의 복호화된 ID와 대조하여:

```
network Item ID
→ ItemRecord.m_id 복호화
→ m_nameId
→ Word__krRecord
→ 실제 한국어 명칭
```

테이블을 만드는 것이다.

### 2순위 — Equipment

이미:

```
41000000 → 141000000
```

가 확인됐고 Ghidra의 `MergeEquip → EquipInfo.Refresh`까지 연결됐다.

다음은 실제 Bootstrap에서 Equipment entry가 들어 있는 protobuf field를 찾아야 한다.

### 3순위 — Weapon

이미:

```
40000000 → 140000000
```

가 확인됐고:

```
MergeWeapon
    ↓
WeaponInfo ctor
    ↓
WeaponInfo.Refresh
```

가 확인됐다.

다음은 Bootstrap의 어떤 field가 `OpInfo.Weapons`인지 실측한다.

### 4순위 — Hero

`UpdateHeroInfo → HeroInfo.InitHero`를 기준으로 입력 객체의 실제 구조를 역추적한다.

특히 다음 값을 찾는다.

- Hero ID
- Level
- EXP
- Star
- Weapon 연결
- Equipment 연결
- 호출/보유 상태

## 21. 이번 단계의 결론

이번 분석으로 코드데이터 분석은 단순한 `protobuf field 번호 추정` 단계에서 벗어났다.

현재 실증된 핵심은 다음 네 가지다.

1. `ProccessRequestRes`가 OpInfo의 +0x98/+0xA0/+0xA8을 각각 Item/Weapon/Equipment 병합 함수로 직접 전달한다.
2. Item/Weapon/Equipment의 Unity 정적 데이터 `m_id`는 `hiddenValue XOR currentCryptoKey`로 실제 네트워크 ID를 복원할 수 있다.
3. 네트워크 ID와 명칭/설명 코드의 관계가 실제 데이터에서 `ID → 1ID / 2ID` 형태로 확인된다.
4. Item은 `field 21 → OpInfo.Items → MergeItem → Dictionary → BaseData → Warehouse UI`까지 하나의 처리 그래프로 연결됐다.

따라서 앞으로는 코드번호를 임의로 생성하거나 추측하지 않고:

```
실제 네트워크 ID
    ↕
Unity m_id 복호화
    ↕
Item/Weapon/Equipment Record
    ↕
Name/Describe/Type 코드
    ↕
Word__krRecord
    ↕
실제 게임 명칭
```

의 양방향 매핑을 구축하는 방향으로 진행한다.
