# 코드데이터 역매핑 분석 트랙 — GPT 자문

**작성일**: 2026-10-02  
**목적**: 서버 구현 트랙과 분리하여 Item / Hero / Weapon / Equipment 등 게임 코드데이터의 protobuf ↔ 런타임 객체 ↔ UI 연결관계를 역분석한다.

## 1. 분석 트랙 분리

현재 서버 트랙은 Bootstrap Replay + Surgical Patch까지 성공했으므로 서버 구현은 별도 진행한다.

이 문서는 다음 분석만 담당한다.
- Bootstrap protobuf의 데이터 필드 구조
- OpInfo 각 데이터 객체와 protobuf field의 대응관계
- Ghidra에서 Proto 계열 클래스/함수의 생성·병합·저장 흐름
- Frida 런타임에서 실제 객체와 UI 전달 흐름
- Surgical Patch를 이용한 의미 검증

분석 대상 우선순위:
1. Currency
2. Item
3. Hero
4. Weapon
5. Equipment
6. Chapter
7. Team / Quest / 기타

## 2. 현재 확정된 기준선

### 2.1 네트워크/Bootstrap

운영 Bootstrap Replay로 실제 Main 화면 진입에 성공했다.
또한 실측 Bootstrap의 특정 protobuf 값만 변경하는 Surgical Patch가 성공했다.

대표 사례:
- field 38의 currency entry
- currency ID 43000001
- amount 35025 → 999999
- 실제 게임 UI에서 999,999 표시 확인

따라서 현재는 protobuf를 처음부터 Builder로 만들 필요 없이, 실측 응답을 분석용 기준 데이터로 사용한다.

### 2.2 OpInfo

런타임에서 확인된 주요 필드:
- User +0x88
- Heros +0x90
- Items +0x98
- Weapons +0xA0
- Equiments +0xA8
- Mails +0xB0
- Olds +0xB8
- Chapters +0xC0
- Sections +0xC8
- Teams +0xD0
- ViewItems +0xD8
- Fashions +0xE0
- Quests +0xE8
- Shops +0xF0
- Charges +0xF8
- Friends +0x100
- Exam +0x108
- Rival +0x110
- Ranks +0x118
- Activities +0x120

주의: 위 값은 C# 객체 메모리 오프셋이며 protobuf field 번호가 아니다.

## 3. 현재 Bootstrap protobuf에서 확인된 최상위 field

실측 Bootstrap에는 다음 field들이 존재한다.

1, 2, 4, 5, 12, 13, 14, 15, 21, 35, 37, 38, 39, 40, 43, 44, 45, 48, 49, 51, 56

| protobuf field | 런타임 의미 | 근거 | 상태 |
|---|---|---|---|
| 21 | Items | 276개 entry, 각 entry {f1=ID, f2=count}, OpInfo.Items 경로와 일치 | 확정 수준 |
| 35 | User | UserID/username을 포함한 User 구조 | 확정 |
| 38 | Currency | 35개 currency entry, Gold ID 43000001의 amount 변경이 실제 UI에 반영 | 실증 확정 |
| 43 | Chapters | 61개 entry, Chapter 런타임 구조와 대응 | 확정 수준 |
| 37/39/40/44/45/48/49/51/56 | 미확정 | 구조 분석 필요 | 미확정 |

## 4. 분석 방법

단일 근거로 field 의미를 결정하지 않는다.
각 데이터는 protobuf, Ghidra, Runtime 세 방향을 교차검증한다.

protobuf → field / nested field / ID / count / value

Ghidra → Proto 클래스 / Deserialize / Merge / Dictionary / List / cache

Runtime → OpInfo 객체 → DataCenter → UI

A + B + C가 일치하면 확정, A만 일치하면 추정으로 기록한다.

## 5. Item 분석

현재 가장 좋은 출발점이다.

### 5.1 알려진 구조

Bootstrap field 21
- repeated bytes × 276
- 각 entry: field 1 = Item ID, field 2 = Count

### 5.2 다음 목표

대표 Item 5~10개를 선정한다.
각 Item에 대해 protobuf의 Item ID/Count 기록 → 런타임 ProtoItem/object 변환 추적 → DataCenter.MergeItem 경로 확인 → Warehouse cache 저장 구조 확인 → Warehouse UI 표시 데이터 연결 → Count surgical patch로 UI 반영 여부 확인.

목표 경로:
field 21 → ProtoItem → OpInfo.Items → MergeItem → DataCenter cache → Warehouse → UI

## 6. Hero 분석

Item 다음으로 OpInfo.Heros를 직접 추적한다.
우선 Ghidra에서 다음 문자열/함수/타입을 검색한다.
OpInfo / Hero / ProtoHero / Heros / MergeHero / Dictionary / List

확인 대상:
- Hero 객체 생성 위치
- Deserialize 직후 Hero 데이터가 저장되는 함수
- OpInfo.Heros 대입 지점
- Hero ID
- Level
- Rank/rarity
- EXP
- 성장 관련 수치
- 장착 Weapon/Equipment와의 연결

protobuf field는 개수만 보고 추측하지 않는다.

## 7. Weapon / Equipment 분석

Hero 분석에서 확보한 ID와 연결관계를 이용한다.
우선순위: OpInfo.Weapons → ProtoWeapon, OpInfo.Equiments → ProtoEquipment/ProtoEquiment

특히 Equipment는 게임 내부 표기에서 Equiments로 되어 있을 가능성이 있으므로 Ghidra 검색 시 오탈자까지 그대로 사용한다.

## 8. Surgical Patch 실험 원칙

실험에서는 한 번에 한 값만 변경한다.
좋은 실험: 원본 Item Count = 10, 패치 Item Count = 999, 나머지 데이터는 원본 그대로.
나쁜 실험: Item + Hero + Weapon + gzip + KCP를 동시에 변경.

판정:
- UI 값 변경 → 데이터 의미 강하게 확정
- 런타임 객체 값 변경만 확인 → 구조 확정에 가까운 증거
- protobuf만 변경되고 UI 변화 없음 → 중간 변환/캐시/조건 확인
- TryRead 실패 → protobuf 구조 자체 또는 serialization 문제부터 재검증

## 9. Ghidra 분석 우선 검색어

ProtoItem, ProtoHero, ProtoWeapon, ProtoEquipment, ProtoEquiment, MergeItem, MergeHero, MergeWeapon, MergeEquipment, MergeEquiment, OpInfo, Heros, Items, Weapons, Equiments

함수명을 검색할 때는 프로젝트의 Ghidra 파일 그룹 규칙을 따른다.
파일 그룹은 namespace를 포함한 전체 함수명의 시작 2글자를 기준으로 한다. < > $는 _로 치환되어 있다.
예: Alioth.S1.Net.KCPTube$$TryRead → AL.txt

## 14. 2026-10-02 실제 Ghidra 처리경로 추적 결과

이번 단계에서는 계획 단계에 머물지 않고 Ghidra Listing의 실제 호출 관계를 추적했다.

### 14.1 DataCenter.ProccessRequestRes → 각 OpInfo 데이터의 직접 전달

확인 함수:

`DataCenter$$ProccessRequestRes @ 0x016e203c`

해당 함수의 실제 호출부에서 다음 관계가 확인된다.

```
OpInfo + 0xA0 (Weapons)
    ↓
DataCenter$$MergeWeapon @ 0x016e414c

OpInfo + 0xA8 (Equiments)
    ↓
DataCenter$$MergeEquip @ 0x016e4348

OpInfo + 0x98 (Items)
    ↓
DataCenter$$MergeItem @ 0x016e4700

OpInfo + 0x90 (Heros)
    ↓
DataCenter$$UpdateHeroInfo @ 0x016e4ba4
```

실제 Listing:

```
016e29dc  ldr x0,[x20, #0x40]
016e29e0  ldr x1,[x26, #0xa0]
016e29e4  bl 0x016e414c

016e29e8  ldr x0,[x20, #0x38]
016e29ec  ldr x1,[x26, #0xa8]
016e29f0  bl 0x016e4348

016e29f4  ldr x1,[x26, #0x98]
016e29f8  mov x0,x20
016e29fc  bl 0x016e4700

016e2a00  mov x0,x20
016e2a04  mov x1,x26
016e2a08  bl 0x016e4ba4
```

여기서 `x26`은 Response로부터 만들어진 OpInfo 객체이며, 기존 runtime 관측의 +0x90/+0x98/+0xA0/+0xA8과 정확히 연결된다.

따라서 다음은 더 이상 단순 추정이 아니다.

| Runtime OpInfo | 실제 처리 함수 | 상태 |
|---|---|---|
| +0x90 Heros | UpdateHeroInfo | **Ghidra 직접 확인** |
| +0x98 Items | MergeItem | **Ghidra 직접 확인** |
| +0xA0 Weapons | MergeWeapon | **Ghidra 직접 확인** |
| +0xA8 Equiments | MergeEquip | **Ghidra 직접 확인** |

### 14.2 Item 처리 경로

`DataCenter$$MergeItem @ 0x016e4700`

호출자는:

```
DataCenter$$ProccessRequestRes
    ↓
MergeItem(DataCenter, OpInfo.Items)
```

MergeItem 내부에서 확인된 주요 동작:

- `Dictionary<int, object>` 접근
- 기존 항목 `get_Item / set_Item`
- `Dictionary<Int32Enum, object>` 접근
- `DataManager$$TryGetBaseData`
- 기존 항목 제거 `Dictionary.Remove`
- enumerate를 통한 기존 cache와 신규 데이터 병합

즉 Item은 단순히 protobuf 목록을 UI에 직접 전달하는 것이 아니라:

```
OpInfo.Items
    ↓
DataCenter.MergeItem
    ↓
ID 기반 Dictionary cache
    ↓
BaseData 조회
    ↓
Warehouse/UI
```

형태로 정리된다.

### 14.3 Warehouse가 실제로 사용하는 DataCenter cache

`WareHousePanelMono$$RefreshWareHouse @ 0x0104c1f8`에서:

```
0104c234  ldr x8,[x22]
0104c238  ldr x8,[x8, #0xb8]
0104c23c  ldr x0,[x8, #0x90]
```

가 확인된다.

즉 Warehouse는 DataCenter singleton에서 특정 cache/object를 얻은 뒤 `InitData`/UI 갱신으로 연결한다.

`WareHousePanelMono$$InitData @ 0x0104ace0`에서는:

- `Dictionary<int, object>.Values`
- `Where`
- `OrderByDescending`
- `ToList`

가 확인된다.

따라서 Warehouse의 표시 목록은 **ID→객체 Dictionary의 Values를 필터/정렬하여 만든 List**라는 점이 정적 분석으로 확인됐다.

`WareHousePanelMono$$ShowGoods @ 0x0104d6e8`에서는 최종적으로:

```
List<object>
    ↓ ToArray
    ↓ LoopScrollRect.objectsToFill
    ↓ ClearCells
    ↓ RefillCells
```

로 UI에 공급된다.

### 14.4 Item UI가 참조하는 실제 코드데이터

`ItemShowNormalMono$$SetItem @ 0x00eb0ddc`에서 다음 호출들이 확인된다.

- `DataManager$$TryGetBaseData`
- `BaseData$$get_icon`
- `BaseData$$get_NameByWord`
- `BaseData$$get_type`
- `BaseData$$get_quality`
- `BaseData$$get_star`
- `BaseData$$get_specialShow`
- `AliothExtensions$$SetSprite`
- `AliothExtensions$$SetTextExt`

따라서 Item의 네트워크 ID가 UI에 도달하면 최종 표시명은 별도의 `Word` 데이터와 `BaseData`를 통해 해결된다.

이는 다음 구조를 지지한다.

```
network Item ID
    ↓
Item runtime object
    ↓
DataManager.GetBaseData(ID)
    ↓
BaseData
    ├─ icon
    ├─ quality
    ├─ type
    ├─ star
    └─ NameByWord
             ↓
        Word__krRecord
```

## 15. Unity 코드데이터의 암호화 해제와 네트워크 ID 실증

Unity 원본 `ItemRecord.json`에서 다음 데이터를 직접 확인했다.

첫 Item:

```
currentCryptoKey = 444444
hiddenValue      = 43444445
m_icon           = item_43000001
m_nameId         = 143000001
m_describeId     = 243000001
```

계산:

```
43444445 XOR 444444 = 43000001
```

두 번째/세 번째 Item도 동일하다.

```
43444446 XOR 444444 = 43000002
43444447 XOR 444444 = 43000003
```

따라서 Item의 `m_id`는 단순 저장값이 아니라:

```
network ID = hiddenValue XOR currentCryptoKey
```

형태로 복원되는 것으로 실증됐다.

이 결과는 사용자가 제시한 `currentCryptoKey + hiddenValue` 기반 코드 분석 방향과 일치한다.

### 15.1 Equipment에서도 동일한 규칙 확인

`EquipmentRecord.json` 첫 항목:

```
currentCryptoKey = 444444
hiddenValue      = 41374812
m_icon           = equip_41000000
m_nameId         = 141000000
```

계산:

```
41374812 XOR 444444 = 41000000
```

다음 항목:

```
41374813 XOR 444444 = 41000001
41374814 XOR 444444 = 41000002
```

즉 Equipment 네트워크 ID 계열은 `41xxxxxx`이며, Unity 정적 데이터의 ID와 직접 연결된다.

### 15.2 Weapon에서도 동일한 규칙 확인

`WeaponRecord.json` 첫 항목:

```
currentCryptoKey = 444444
hiddenValue      = 40145436
m_icon           = w_t_10000
m_nameId         = 140000000
m_code           = 10000
```

계산:

```
40145436 XOR 444444 = 40000000
```

다음 항목도:

```
40145437 XOR 444444 = 40000001
40145438 XOR 444444 = 40000002
```

따라서 Weapon 네트워크 ID 계열은 `40xxxxxx`이다.

## 16. 사용자가 제시한 1/2/3/4 접두어 규칙과의 실데이터 대조

현재 실제 Unity 원본에서 다음 대응이 확인된다.

### Item

```
network ID : 43000001

name       : 143000001
describe   : 243000001
```

### Equipment

```
network ID : 41000000

name       : 141000000
describe   : 0
```

### Weapon

```
network ID : 40000000

name       : 140000000
describe   : 0
```

즉:

```
네트워크 코드 = XXXXXXXXX
명칭 코드    = 1 + 네트워크 코드
설명 코드    = 2 + 네트워크 코드
```

라는 관계가 Item 데이터에서 직접 관측되고, Equipment/Weapon에서도 명칭 계열이 같은 방식으로 맞는다.

따라서 사용자가 제시한:

```
52000100
→ 152000100
→ 252000100
→ 352000100
→ 452000100 ...
```

규칙은 현재까지 확보한 실제 데이터와 **구조적으로 일치한다**.

단, `52000100` 자체의 실제 레코드와 3/4 계열 필드까지 직접 확인하기 전에는 해당 개별 코드에 대해 확정 판정을 내리지 않는다.

현재 판정:

- 접두어 기반 계열 규칙: **강한 실증**
- Item 43000001 → 143000001/243000001: **실증 확정**
- Equipment 41000000 → 141000000: **실증**
- Weapon 40000000 → 140000000: **실증**
- 52000100 개별 사례: **미확정**

## 17. Hero 분석 방향 수정

Hero는 `DataCenter$$MergeHero`라는 별도 함수가 존재하지 않는다.

현재 직접 확인된 진입점은:

```
DataCenter$$ProccessRequestRes
    ↓
DataCenter$$UpdateHeroInfo @ 0x016e4ba4
    ↓
HeroInfo$$InitHero @ 0x016e5fd4
    ↓
HeroInfo / DataManager / cache
```

UpdateHeroInfo에서 확인된 호출:

- `Dictionary<int, object>.TryGetValue`
- `HeroInfo$$InitHero`
- `HeroInfo$$FinalUpgradeHero`
- `DataManager$$TryGet<object>`
- `DataCenter$$ConfirmCallHero`
- HashSet<int> 관리
- Dictionary enumeration

따라서 Hero는 Item/Weapon/Equipment처럼 `MergeHero`를 찾는 방식이 아니라 **UpdateHeroInfo → InitHero**를 중심으로 추적해야 한다.

## 21. 이번 단계의 결론

이번 분석으로 코드데이터 분석은 단순한 `protobuf field 번호 추정` 단계에서 벗어났다.

현재 실증된 핵심은 다음 네 가지다.

1. `ProccessRequestRes`가 OpInfo의 +0x98/+0xA0/+0xA8을 각각 Item/Weapon/Equipment 병합 함수로 직접 전달한다.
2. Item/Weapon/Equipment의 Unity 정적 데이터 `m_id`는 `hiddenValue XOR currentCryptoKey`로 실제 네트워크 ID를 복원할 수 있다.
3. 네트워크 ID와 명칭/설명 코드의 관계가 실제 데이터에서 `ID → 1ID / 2ID` 형태로 확인된다.
4. Item은 `field 21 → OpInfo.Items → MergeItem → Dictionary → BaseData → Warehouse UI`까지 하나의 처리 그래프로 연결됐다.

따라서 앞으로는 코드번호를 임의로 생성하거나 추측하지 않고:

```
실제 네트워크 ID
    ↕
Unity m_id 복호화
    ↕
Item/Weapon/Equipment Record
    ↕
Name/Describe/Type 코드
    ↕
Word__krRecord
    ↕
실제 게임 명칭
```

의 양방향 매핑을 구축하는 방향으로 진행한다.


## 22. Bootstrap field 37/39/40 실측 구조 추가 분석

기준 문서 `research/reports/gpt에서로그인이후데이터분석자료/2026-10-02-Bootstrap-Client-State-MainUI-연결분석.md`를 상위 기준으로 삼아, 기존 code_gen 문서의 초기 field 매핑을 재검증했다.

### 22.1 Field 37 = Hero collection

운영 PCAP의 `messages.json`에서 Bootstrap packet 192~201 응답의 field 37은 4개 entry로 확인된다.

대표 구조:

```
field 37
  ├─ field 1 = HeroId
  └─ field 2 = Hero state
       ├─ field 1 = HeroId
       ├─ field 3 = 4 / 상태 계열
       ├─ field 4 = Level
       ├─ field 5 = Star 계열
       ├─ field 8 = WeaponId
       └─ field 14 = FashionId / 관련 ID 계열
```

실측 예:

| HeroId | nested field 3 | field 4 | field 5 | field 8 | field 14 |
|---:|---:|---:|---:|---:|---:|
| 10000000 | 4 | 140 | 1 | 40000000 | 49000000 |
| 10000001 | 4 | 90 | 1 | 40000100 | 49000100 |
| 10000002 | 2 | - | 1 | 40000200 | 49000200 |
| 10000016 | 1 | - | 1 | 40001603 | 49001600 |

Ghidra에서 `ProtoHeroSnapshot`의 accessor가 확인되어 있다.

- HeroId: +0x10
- Level: +0x14
- Star: +0x18

따라서 field 37의 nested field 1/4/5는 각각 HeroId/Level/Star와 직접 대응하는 구조로 판단할 수 있다. field 8은 실측값이 `40xxxxxx`이고 Bootstrap field 39의 Weapon ID와 일치하므로 **Hero의 장착 WeaponId**로 연결하는 근거가 매우 강하다.

판정:
- field 37 → OpInfo.Heros → UpdateHeroInfo: **정적 확정**
- field 37 nested field 1 → HeroId: **강한 실증 / accessor 구조 일치**
- field 37 nested field 4 → Level: **강한 실증 / accessor 구조 일치**
- field 37 nested field 5 → Star: **강한 실증 / accessor 구조 일치**
- field 37 nested field 8 → WeaponId: **강한 실증**
- field 37 nested field 14 → FashionId 계열: **후속 accessor 확인 필요**

### 22.2 Field 39 = Weapon collection

Bootstrap field 39는 초기 응답에서 4개 entry가 확인된다.

대표값:

| WeaponId | nested field 3 | nested field 4 | nested field 5 |
|---:|---:|---:|---:|
| 40000000 | 1 | 180 | 1 |
| 40000100 | 1 | 160 | 1 |
| 40000200 | 1 | 20 | 1 |
| 40001603 | 1 | 생략 | 1 |

Ghidra `ProtoWeapon` accessor는 다음 메모리 구조를 갖는다.

- Id +0x10
- Status +0x14
- Level +0x18
- Exp +0x1C
- SkillLevel +0x20

따라서 현재 wire 구조는 다음과 같이 연결된다.

```
field 39 entry
  field 1 → ProtoWeapon.Id
  field 2 → ProtoWeapon state
      field 1 → Id
      field 3 → Status
      field 4 → Level
      field 5 → Exp
```

특히 `40000000`, `40000100`, `40000200`, `40001603`은 Unity `WeaponRecord.json`에서 XOR 복호화로 확인한 Weapon 네트워크 ID namespace `40xxxxxx`와 직접 일치한다.

판정:
- field 39 → OpInfo.Weapons → MergeWeapon: **정적 확정**
- nested field 1 → WeaponId: **실증 확정 수준**
- nested field 3 → Status: **Ghidra accessor 구조상 강한 확정**
- nested field 4 → Level: **Ghidra accessor 구조상 강한 확정**
- nested field 5 → Exp: **Ghidra accessor 구조상 강한 확정**
- SkillLevel wire tag는 현재 bootstrap sample에서 확인되지 않음: **미확정/생략 가능**

### 22.3 Field 40 = Equipment collection

Bootstrap field 40은 Weapon과 구조가 다르다. 초기 응답에서는 13개 entry가 확인되고, 대표 구조는 다음과 같다.

```
field 40 entry
  ├─ field 1 = 1-byte string key (예: '#', '$', '%', ...)
  └─ field 2 = nested object
       └─ field 3 = EquipmentId
```

실측 EquipmentId 예:

```
41005000
41005001
41000001
41003001
41002001
41003100
41004011
41005040
41005002
41002100
41005041
41000002
...
```

Ghidra `ProtoEquipment` accessor 구조:

- Id +0x10
- Status +0x18
- EquipmentId +0x1C
- HeroId +0x20
- State +0x24

여기서 중요한 점은 현재 field 40 wire entry가 `ProtoEquipment` 전체 객체를 모두 전송하는 형태가 아니라, **Dictionary/map 형태의 외부 key + 최소 EquipmentId payload**로 관측된다는 것이다. 따라서 field 40의 field 1 문자열을 EquipmentId 자체나 장비 명칭으로 해석하지 않는다.

EquipmentId는 실제 Unity `EquipmentRecord.json`의 XOR 복호화 ID namespace `41xxxxxx`와 일치한다.

판정:
- field 40 → OpInfo.Equiments → MergeEquip: **정적 확정**
- nested field 3 → EquipmentId: **강한 실증**
- outer field 1 string key의 의미: **미확정**
- ProtoEquipment의 Status/HeroId/State와 field 40의 다른 wire tag 대응: **미확정**

### 22.4 Hero ↔ Weapon ↔ Equipment 연결의 중요한 결과

Bootstrap field 37의 Hero entry 자체가 WeaponId를 가지고 있다.
예를 들어:

```
Hero 10000000
  └─ field 8 = 40000000

Hero 10000001
  └─ field 8 = 40000100

Hero 10000002
  └─ field 8 = 40000200

Hero 10000016
  └─ field 8 = 40001603
```

동일 Bootstrap의 field 39에 동일 WeaponId들이 존재한다.

따라서 서버 데이터 모델에서는 Hero와 Weapon을 단순히 독립 목록으로 취급하면 안 되고:

```
HeroId
  ↓ field 37
Hero state
  └─ WeaponId
       ↓ field 39
     Weapon state
```

형태의 연결을 유지해야 한다.

Equipment도 별도 field 40에서 EquipmentId를 제공하지만, 현재 확보된 field 40 sample만으로 특정 EquipmentId가 어느 Hero에 장착됐는지까지는 확정하지 않는다. ProtoEquipment의 HeroId accessor가 존재하므로, 향후 더 풍부한 Equipment 응답 또는 runtime 객체에서 이 연결을 직접 확인한다.

### 22.5 코드 namespace 역매핑 실측 갱신

현재 Bootstrap과 Unity 원본을 동시에 대조하면 다음 namespace가 직접 연결된다.

| 대상 | Network ID sample | Unity Record | 명칭 코드 sample |
|---|---:|---|---:|
| Hero | 10000000 | Hero 계열 추가 확인 필요 | 추가 확인 필요 |
| Weapon | 40000000 | WeaponRecord | 140000000 |
| Equipment | 41000000 계열 | EquipmentRecord | 141000000 계열 |
| Item/Currency | 43000001 등 | ItemRecord | 143000001 계열 |

즉 현재 서버 데이터 구축 시 최소한 다음 namespace를 분리하는 것이 안전하다.

```
10xxxxxx = Hero
40xxxxxx = Weapon
41xxxxxx = Equipment
43xxxxxx = Item/Currency 계열
49xxxxxx = Hero 부속/Fashion 계열 후보
```

단, `49xxxxxx`는 field 37 nested field 14에서 관측된 값이라는 이유만으로 Fashion 전체 namespace라고 확정하지 않는다.

### 22.6 다음 분석 우선순위 수정

1. **HeroRecord 원본 확보**: `10000000` 계열을 currentCryptoKey/hiddenValue로 복호화해 HeroId와 field 37 속성을 연결한다.
2. **Hero field 14 확인**: 49000000 계열이 실제 FashionId인지 관련 Record와 accessor로 검증한다.
3. **Equipment outer key 분석**: field 40의 '#', '$', '%' 등의 key가 어떤 의미인지 `MergeEquip` 내부의 KeyValuePair 처리와 runtime 객체를 연결한다.
4. **Equipment HeroId 연결**: ProtoEquipment.HeroId(+0x20)가 실제 wire field로 언제 전달되는지 다른 응답/실행 로그에서 확인한다.
5. **Weapon SkillLevel**: ProtoWeapon +0x20에 대응하는 wire tag를 다른 Weapon 응답에서 확인한다.
6. **Item field 38 역매핑**: 43000001/43000002/43000003 외 실제 43xxxxxx item들을 ItemRecord와 대조하여 명칭/유형까지 테이블화한다.

### 22.7 이번 단계 판정

이번 단계에서 기존 code_gen 문서의 초기 판단 중 `field 21 = Item`은 폐기한다.

최종 기준은:

```
field 21 = DictI32 / UserInfo vary + 일부 DataCenter 상태
field 37 = Hero
field 38 = Item
field 39 = Weapon
field 40 = Equipment
field 43 = Chapter
field 44 = Section
field 45 = Team
field 51 = Quest
field 56 = Activity
```

이제 코드데이터 역매핑은 이 field 계약을 기준으로 진행한다.


## 23. 과거 `system_mapping` 분석 결과의 재활용 및 현재 데이터와의 대조

이번 분석에서는 사용자가 지정한 과거 산출물
`참고용-unity-behavior-data/데이터_분석/output/system_mapping`
을 참고 인덱스로 추가 조사했다.

### 23.1 system_mapping 자체의 신뢰 범위

`00_mapping_summary.json` 기준:

- parsed JSON: 74개
- unique record IDs: 118,015
- mapping rows: 11,847
- localization rows: 118,015
- localization conflicts: 0
- item mapping: 952
- item_package: 2,028
- reward: 1,503
- draw: 3,034
- shop: 154
- daily: 3,393
- achievement: 682
- event: 101

당시 분석 규칙에도 다음이 명시되어 있다.

- `hiddenValue XOR currentCryptoKey`를 obscured ID 해제 규칙으로 사용
- 한국어 이름은 `__krRecord.json`의 `m_cn` 사용
- Reference 연결만으로 의미를 확정하지 않음
- 확률/수량/가격은 자동 추정하지 않음

따라서 이 결과는 현재 분석과 방법론적으로 상당히 잘 맞는다.

다만 당시에는 현재처럼 **Bootstrap protobuf field → OpInfo → Merge → UI**의 런타임 계약이 확정되지 않았고, 1/2/3/4 명칭 코드 규칙도 네트워크 데이터와 직접 연결하지 못했다.

따라서 `system_mapping`은 최종 판정 데이터가 아니라 다음 용도로 사용한다.

1. Record 종류/ID 탐색
2. Record 간 참조관계 탐색
3. `m_nameId`, `m_describeId` 등의 실제 field 확인
4. 특정 네트워크 ID 후보가 어느 Record인지 확인
5. 현재 protobuf/런타임 분석에서 찾은 ID를 Unity 원본으로 역검증

### 23.2 52000100 계열은 현재 규칙을 직접 지지한다

`all_system_mappings.ndjson`에서 실제로 다음 연결이 관측된다.

```

  ├─ m_nameId      → 152000100
  ├─ m_describeId  → 252000100
  ├─ m_groupNameId → 352000100
  └─ m_subNameId   → 452000100
```

그리고 다음 ID들도 같은 패턴으로 연결된다.

```
52000101
  ├─ 152000101
  ├─ 252000101
  ├─ 352000100
  └─ 452000100

52000102
  ├─ 152000102
  ├─ 252000102
  ├─ 352000100
  └─ 452000100
```

즉 사용자가 처음 제시한:

```
52000100
→ 152000100
→ 252000100
→ 352000100
→ 452000100
```

이라는 규칙은 이제 단순한 경험칙이 아니라 **Unity Record의 실제 field reference에서 관측된 구조**로 승격할 수 있다.

판정:

- `52000100 → 152000100`: **실증 확정**
- `52000100 → 252000100`: **실증 확정**
- `52000100 → 352000100`: **실증 확정**
- `52000100 → 452000100`: **실증 확정**
- prefix 1/2/3/4가 각각 모든 데이터 종류에서 항상 같은 의미라는 일반화: **아직 미확정**

### 23.3 Item도 동일한 방식으로 system_mapping에서 확인됨

`system_mapping/item/item_mapping.ndjson` 및 `all_system_mappings.ndjson`에서:

가 실제 연결로 기록되어 있다.

이는 앞서 Unity `ItemRecord.json`에서 XOR로 복원한 결과와 정확히 일치한다.

즉 Item에 대해서는 다음 세 경로가 독립적으로 만난다.

```
Bootstrap
  field 38
      ↓
OpInfo.Items
      ↓
DataCenter.MergeItem
      ↓
network Item ID = 43000001
      ↓
ItemRecord
      ↓

m_describeId = 243000001
      ↓

```

### 23.4 system_mapping이 현재 분석에 특히 유용한 이유

과거 분석은 명칭 코드를 몰랐기 때문에 결과가 다음 수준에 머물렀다.

```

  ↓
참조 Record
```

현재는 여기에 네트워크/런타임 계층을 추가할 수 있다.

```
[Bootstrap protobuf]
        ↓
[OpInfo]
        ↓
[Merge / Update]
        ↓
[Runtime ID]
        ↓
[Unity Record ID]
        ↓
[m_nameId / m_describeId / m_type ...]
        ↓
[Word__krRecord]
        ↓
[실제 한국어 명칭]
```

따라서 `system_mapping`은 버릴 과거 자료가 아니라 **현재 분석의 Record graph 데이터베이스로 재활용하는 것이 적절하다.**

### 23.5 서버 구축에 적용할 때의 주의점

현재부터 서버 데이터 생성에 사용하는 매핑은 다음 우선순위를 적용한다.

| 근거 | 용도 | 판정 |
|---|---|---|
| 실제 Bootstrap protobuf | 네트워크 field/값 | 최우선 |
| Ghidra Merge/Update 경로 | 런타임 소비 관계 | 최우선 |
| Runtime/UI 실험 | 의미 검증 | 최우선 |
| Unity Record 원본 | ID/명칭/속성 | 최우선 |
| system_mapping | Record 참조 탐색 | 보조/교차검증 |
| 과거 추정 문서 | 탐색 방향 | 참고만 |

따라서 `system_mapping`에 어떤 연결이 있다고 해서 그것만으로 서버 응답 field를 결정하지 않는다.

### 23.6 다음 실제 작업

현재 가장 생산적인 작업은 전체 118,015개 ID를 한꺼번에 처리하는 것이 아니다.

먼저 Bootstrap에서 실제 보유/사용 중인 ID를 추출한 뒤:

```
Bootstrap ID
→ Record ID 검색
→ hiddenValue XOR currentCryptoKey 검증
→ m_nameId / m_describeId / 추가 field 추출
→ Word__krRecord의 m_cn 확인
```

순으로 소규모 검증 테이블을 만드는 것이다.

우선 대상:

1. field 38의 Item/Currency ID
2. field 39의 Weapon ID
3. field 40의 Equipment ID
4. field 37의 Hero ID 및 장착 WeaponId
5. Hero의 Weapon/Equipment 연결
6. 이후 Chapter/Quest/Activity의 ID graph

이 방식으로 진행하면 과거 `system_mapping`이 가지고 있던 대규모 Record 관계망과 현재 실측 네트워크 데이터가 결합된다.

### 23.7 현재 결론

`system_mapping`은 현재 분석에 **도움이 되는 정도가 아니라, 앞으로 반드시 활용할 가치가 있는 기존 자산**이다.

특히 `52000100`과 `43000001`의 명칭/설명 코드 연결이 이미 실제 Record reference로 존재하므로, 앞으로는 이 데이터를 이용해:

```
네트워크 ID
↔ Unity Record
↔ 명칭 코드
↔ 한국어 명칭
```

의 자동/반자동 역매핑 테이블을 구축하는 방향이 가장 효율적이다.

단, 과거 system_mapping의 `confidence=observed`는 **Record reference가 관측되었다는 뜻**으로 해석하고, 네트워크 field 의미나 런타임 소비까지 확정했다는 뜻으로 확대해석하지 않는다.
