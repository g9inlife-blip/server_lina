# 코드데이터 역매핑 분석 트랙 — GPT 자문

**작성일**: 2026-10-02  
**목적**: 서버 구현 트랙과 분리하여 Item / Hero / Weapon / Equipment 등 게임 코드데이터의 protobuf ↔ 런타임 객체 ↔ UI 연결관계를 역분석한다.

## 1. 분석 트랙 분리

현재 서버 트랙은 Bootstrap Replay + Surgical Patch까지 성공했으므로 서버 구현은 별도 진행한다.

이 문서는 다음 분석만 담당한다.
- Bootstrap protobuf의 데이터 필드 구조
- OpInfo 각 데이터 객체와 protobuf field의 대응관계
- Ghidra에서 Proto 계열 클래스/함수의 생성·병합·저장 흐름
- Frida 런타임에서 실제 객체와 UI 전달 흐름
- Surgical Patch를 이용한 의미 검증

분석 대상 우선순위:
1. Currency
2. Item
3. Hero
4. Weapon
5. Equipment
6. Chapter
7. Team / Quest / 기타

## 2. 현재 확정된 기준선

### 2.1 네트워크/Bootstrap

운영 Bootstrap Replay로 실제 Main 화면 진입에 성공했다.
또한 실측 Bootstrap의 특정 protobuf 값만 변경하는 Surgical Patch가 성공했다.

대표 사례:
- field 38의 currency entry
- currency ID 43000001
- amount 35025 → 999999
- 실제 게임 UI에서 999,999 표시 확인

따라서 현재는 protobuf를 처음부터 Builder로 만들 필요 없이, 실측 응답을 분석용 기준 데이터로 사용한다.

### 2.2 OpInfo

런타임에서 확인된 주요 필드:
- User +0x88
- Heros +0x90
- Items +0x98
- Weapons +0xA0
- Equiments +0xA8
- Mails +0xB0
- Olds +0xB8
- Chapters +0xC0
- Sections +0xC8
- Teams +0xD0
- ViewItems +0xD8
- Fashions +0xE0
- Quests +0xE8
- Shops +0xF0
- Charges +0xF8
- Friends +0x100
- Exam +0x108
- Rival +0x110
- Ranks +0x118
- Activities +0x120

주의: 위 값은 C# 객체 메모리 오프셋이며 protobuf field 번호가 아니다.

## 3. 현재 Bootstrap protobuf에서 확인된 최상위 field

실측 Bootstrap에는 다음 field들이 존재한다.

1, 2, 4, 5, 12, 13, 14, 15, 21, 35, 37, 38, 39, 40, 43, 44, 45, 48, 49, 51, 56

| protobuf field | 런타임 의미 | 근거 | 상태 |
|---|---|---|---|
| 21 | Items | 276개 entry, 각 entry {f1=ID, f2=count}, OpInfo.Items 경로와 일치 | 확정 수준 |
| 35 | User | UserID/username을 포함한 User 구조 | 확정 |
| 38 | Currency | 35개 currency entry, Gold ID 43000001의 amount 변경이 실제 UI에 반영 | 실증 확정 |
| 43 | Chapters | 61개 entry, Chapter 런타임 구조와 대응 | 확정 수준 |
| 37/39/40/44/45/48/49/51/56 | 미확정 | 구조 분석 필요 | 미확정 |

## 4. 분석 방법

단일 근거로 field 의미를 결정하지 않는다.
각 데이터는 protobuf, Ghidra, Runtime 세 방향을 교차검증한다.

protobuf → field / nested field / ID / count / value

Ghidra → Proto 클래스 / Deserialize / Merge / Dictionary / List / cache

Runtime → OpInfo 객체 → DataCenter → UI

A + B + C가 일치하면 확정, A만 일치하면 추정으로 기록한다.

## 5. Item 분석

현재 가장 좋은 출발점이다.

### 5.1 알려진 구조

Bootstrap field 21
- repeated bytes × 276
- 각 entry: field 1 = Item ID, field 2 = Count

### 5.2 다음 목표

대표 Item 5~10개를 선정한다.
각 Item에 대해 protobuf의 Item ID/Count 기록 → 런타임 ProtoItem/object 변환 추적 → DataCenter.MergeItem 경로 확인 → Warehouse cache 저장 구조 확인 → Warehouse UI 표시 데이터 연결 → Count surgical patch로 UI 반영 여부 확인.

목표 경로:
field 21 → ProtoItem → OpInfo.Items → MergeItem → DataCenter cache → Warehouse → UI

## 6. Hero 분석

Item 다음으로 OpInfo.Heros를 직접 추적한다.
우선 Ghidra에서 다음 문자열/함수/타입을 검색한다.
OpInfo / Hero / ProtoHero / Heros / MergeHero / Dictionary / List

확인 대상:
- Hero 객체 생성 위치
- Deserialize 직후 Hero 데이터가 저장되는 함수
- OpInfo.Heros 대입 지점
- Hero ID
- Level
- Rank/rarity
- EXP
- 성장 관련 수치
- 장착 Weapon/Equipment와의 연결

protobuf field는 개수만 보고 추측하지 않는다.

## 7. Weapon / Equipment 분석

Hero 분석에서 확보한 ID와 연결관계를 이용한다.
우선순위: OpInfo.Weapons → ProtoWeapon, OpInfo.Equiments → ProtoEquipment/ProtoEquiment

특히 Equipment는 게임 내부 표기에서 Equiments로 되어 있을 가능성이 있으므로 Ghidra 검색 시 오탈자까지 그대로 사용한다.

## 8. Surgical Patch 실험 원칙

실험에서는 한 번에 한 값만 변경한다.
좋은 실험: 원본 Item Count = 10, 패치 Item Count = 999, 나머지 데이터는 원본 그대로.
나쁜 실험: Item + Hero + Weapon + gzip + KCP를 동시에 변경.

판정:
- UI 값 변경 → 데이터 의미 강하게 확정
- 런타임 객체 값 변경만 확인 → 구조 확정에 가까운 증거
- protobuf만 변경되고 UI 변화 없음 → 중간 변환/캐시/조건 확인
- TryRead 실패 → protobuf 구조 자체 또는 serialization 문제부터 재검증

## 9. Ghidra 분석 우선 검색어

ProtoItem, ProtoHero, ProtoWeapon, ProtoEquipment, ProtoEquiment, MergeItem, MergeHero, MergeWeapon, MergeEquipment, MergeEquiment, OpInfo, Heros, Items, Weapons, Equiments

함수명을 검색할 때는 프로젝트의 Ghidra 파일 그룹 규칙을 따른다.
파일 그룹은 namespace를 포함한 전체 함수명의 시작 2글자를 기준으로 한다. < > $는 _로 치환되어 있다.
예: Alioth.S1.Net.KCPTube$$TryRead → AL.txt

## 10. Frida 분석 목표

현재 justice_hook_opinfo.js의 기존 체크포인트를 유지한다.
운영용 gpt전용_justice_hook_운영접속용.js는 수정하지 않는다.
새 분석용 hook이 필요하면 별도 파일로 만든다.

목표 출력 예:
[CODEMAP] OpInfo.Heros = 0x...
[CODEMAP] OpInfo.Items = 0x...
[CODEMAP] OpInfo.Weapons = 0x...
[CODEMAP] OpInfo.Equiments = 0x...

그 다음 각 객체의 실제 타입/내부 필드/ID를 읽을 수 있는 함수로 확장한다.

## 11. 분석 기록 원칙

각 항목은 다음 상태 중 하나로 관리한다.
- 확정: protobuf + Ghidra + runtime/UI가 일치

- 추정: 구조적 근거만 있음
- 미확정: 추가 분석 필요
- 폐기: 실험으로 반증됨
