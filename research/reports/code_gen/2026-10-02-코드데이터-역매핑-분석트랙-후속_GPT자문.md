# 코드데이터 역매핑 분석 트랙 후속 — GPT 자문

**작성일**: 2026-10-02  
**목적**: `code_gen/2026-10-02-코드데이터-역매핑-분석트랙_GPT자문.md`의 후속 분석. 실제 Ghidra Listing과 PCAP protobuf, Unity 원본 데이터를 교차검증하여 Item / Hero / Weapon / Equipment의 네트워크-런타임 연결을 구체화한다.

---

## 1. 이번 분석에서 확인된 핵심

기존 문서는 분석 시작점만 정의했지만, 이번에는 실제 Ghidra Listing에서 데이터 처리 함수의 호출 관계를 확인했다.

가장 중요한 결과:

```
DataCenter.ProccessRequestRes @ 0x016e203c
        │
        ├─ OpInfo +0xA0 Weapons
        │      └─ DataCenter.MergeWeapon @ 0x016e414c
        │
        ├─ OpInfo +0xA8 Equiments
        │      └─ DataCenter.MergeEquip @ 0x016e4348
        │
        ├─ OpInfo +0x98 Items
        │      └─ DataCenter.MergeItem @ 0x016e4700
        │
        └─ OpInfo +0x90 Heros
               └─ DataCenter.UpdateHeroInfo @ 0x016e4ba4
```

따라서 이전의 단순한 "OpInfo 필드가 존재한다" 수준에서 벗어나 **실제 데이터 처리 함수까지 연결된 상태**다.

상태를 다음과 같이 변경한다.

| 데이터 | Runtime | Ghidra 처리 함수 | protobuf |
|---|---|---|---|
| Item | +0x98 | MergeItem 0x016e4700 | field 21 |
| Hero | +0x90 | UpdateHeroInfo 0x016e4ba4 | field 37 |
| Weapon | +0xA0 | MergeWeapon 0x016e414c | field 39 후보 |
| Equipment | +0xA8 | MergeEquip 0x016e4348 | 미확정 |

## 2. DataCenter.ProccessRequestRes에서 확인한 실제 연결

### 2.1 Item

Ghidra:

```
016e29f4  ldr x1,[x26, #0x98]
016e29f8  mov x0,x20
016e29fc  bl 0x016e4700
```

함수:

```
DataCenter$$MergeItem @ 016e4700
```

즉:

```
ProccessRequestRes
    x26 = OpInfo
    x26 + 0x98 = Items
    x20 = DataCenter
    MergeItem(DataCenter, OpInfo.Items)
```

### 2.2 Weapon

```
016e29dc  ldr x0,[x20, #0x40]
016e29e0  ldr x1,[x26, #0xa0]
016e29e4  bl 0x016e414c
```

함수:

```
DataCenter$$MergeWeapon @ 016e414c
```

따라서:

```
MergeWeapon(DataCenter, OpInfo.Weapons)
```

가 직접 확인된다.

### 2.3 Equipment

```
016e29e8  ldr x0,[x20, #0x38]
016e29ec  ldr x1,[x26, #0xa8]
016e29f0  bl 0x016e4348
```

함수:

```
DataCenter$$MergeEquip @ 016e4348
```

따라서:

```
MergeEquip(DataCenter, OpInfo.Equiments)
```

가 직접 확인된다.

특히 Ghidra 함수명이 `MergeEquip`인 점 때문에 런타임 프로퍼티의 `Equiments` 오탈자와 별개로 처리 함수는 정상적인 `Equip` 명칭을 사용한다.

## 3. Hero 처리 경로는 별도 함수로 확인

Hero는 Item/Weapon/Equipment처럼 `MergeHero`라는 함수가 존재하지 않았다.

대신:

```
DataCenter$$UpdateHeroInfo @ 016e4ba4
```

가 존재한다.

그리고 `ProccessRequestRes`에서:

```
016e2a00  mov x0,x20
016e2a04  mov x1,x26
016e2a08  bl 0x016e4ba4
```

로 호출된다.

즉:

```
UpdateHeroInfo(DataCenter, OpInfo)
```

형태다.

UpdateHeroInfo 내부에서 실제로:

```
016e508c  ldr x0,[x27, #0x90]
```

로 `OpInfo +0x90`을 가져오고, 그 Dictionary를 열거한다.

이후 각 Hero ID에 대해:

```
016e5170  ldr x0,[x27, #0x90]
016e5178  ...
016e518c  mov w1,w22
016e5190  bl 0x0192f460
```

형태로 Dictionary에서 Hero 데이터를 조회한다.

그리고 기존 HeroInfo가 없거나 갱신이 필요한 경우:

```
016e51a0  ldr x1,[sp, #0x40]
016e51a4  bl 0x016e5fd4
```

즉:

```
HeroInfo$$InitHero @ 016e5fd4
```

가 호출된다.

### 결론

Hero 경로는 현재 다음 수준까지 확정한다.

```
OpInfo.Heros (+0x90)
        ↓
UpdateHeroInfo
        ↓
Hero ID Dictionary 순회
        ↓
기존 HeroInfo 조회
        ↓
HeroInfo.InitHero
```

상태: **강한 확정**

## 4. ProtoItem 구조

Ghidra에서 `ProtoItem` getter가 확인된다.

```
ProtoItem$$get_Id    @ 0x015ad444
ProtoItem$$get_Status @ 0x015ad454
ProtoItem$$get_Count @ 0x015ad464
```

메모리:

| Property | Runtime offset |
|---|---:|
| Id | +0x10 |
| Status | +0x14 |
| Count | +0x18 |

실측 protobuf field 21의 대표 entry는:

```
field 21
  field 1 = Item ID
  field 2 = Count
```

이다.

따라서 ProtoItem property 순서와 실측 데이터가 다음과 같이 대응한다.

```
ProtoItem.Id    → protobuf field 1
ProtoItem.Count → protobuf field 2
```

Status는 현재 field 21 실측 entry에서 관측되지 않으므로, **존재 가능한 ProtoItem.Status가 항상 네트워크에 직렬화된다고 가정하지 않는다.**

## 6. ProtoWeapon 구조

Ghidra에서 확인된 ProtoWeapon getter:

```
ProtoWeapon$$get_Id          @ 0x015adc7c
ProtoWeapon$$get_Status      @ 0x015adc8c
ProtoWeapon$$get_Level       @ 0x015adc9c
ProtoWeapon$$get_Exp         @ 0x015adcac
ProtoWeapon$$get_SkillLevel  @ 0x015adcbc
```

Runtime offset:

| Property | Offset |
|---|---:|
| Id | +0x10 |
| Status | +0x14 |
| Level | +0x18 |
| Exp | +0x1C |
| SkillLevel | +0x20 |

따라서 직렬화 field 구조는 현재 다음을 기준으로 조사한다.

```
field 1 = Id
field 2 = Status
field 3 = Level
field 4 = Exp
field 5 = SkillLevel
```

Bootstrap에는 **field 39가 4개** 존재한다.

또한 ProccessRequestRes가 정확히:

```
OpInfo +0xA0
    ↓
MergeWeapon
```

으로 전달하므로 **field 39는 Weapon 데이터일 가능성이 매우 높다.**

그러나 현재 확보된 비압축 후속 PCAP에서는 field 39의 직접 nested 샘플을 찾지 못했으므로 최종 상태는:

**강한 추정**

으로 유지한다.

다음 확정 방법은 Bootstrap field 39의 4개 entry를 직접 protobuf nested dump하여:

```
outer.field1 = Weapon ID
outer.field2.field1 = ProtoWeapon.Id
outer.field2.field3 = Level
outer.field2.field4 = Exp
outer.field2.field5 = SkillLevel
```

패턴을 확인하는 것이다.

| HeroId | +0x20 |
| State | +0x24 |

## 8. 코드데이터 암호화 규칙도 실제 Unity 원본으로 검증

Unity 원본의 `m_id`는:

```
currentCryptoKey
hiddenValue
```

형태다.

ItemRecord에서:

```
currentCryptoKey = 444444
hiddenValue = 43444445
```

일 때:

```
444444 XOR 43444445 = 43000001
```

이므로 네트워크/런타임 코드가 `43000001`로 복원된다.

WeaponRecord에서도:

```
444444 XOR 40145436 = 40000000
```

가 확인된다.

따라서 현재 코드 복호화 규칙은:

```
decodedCode = currentCryptoKey XOR hiddenValue
```

로 **실증 확정**한다.

## 9. 사용자가 제시한 52000100 → 152000100 계열도 원본에서 직접 확인

StigmataRecord에서:

```
currentCryptoKey = 444444
hiddenValue = 52411768
```

이고:

```
52411768 XOR 444444 = 52000100
```

이다.

같은 레코드에는:

```
m_icon        = item_52000000
m_nameId      = 152000100
m_describeId  = 252000100
m_groupNameId = 352000100
m_subNameId   = 452000100
```

가 실제로 존재한다.

즉 사용자가 제시한:

```
52000100
→ 152000100
→ 252000100
→ 352000100
→ 452000100
```

형태는 단순한 가정이 아니라 **Unity 원본 데이터에서 직접 확인되는 실제 코드 관계**다.

이 결과는 앞으로 네트워크 ID를 받은 뒤 명칭/설명/분류 등을 역매핑하는 데 핵심 기준으로 사용한다.

## 10. 현재 코드데이터 분석의 구조

현재까지 가장 신뢰할 수 있는 구조는 다음이다.

```
[Unity 원본 Record]

m_id.currentCryptoKey
m_id.hiddenValue
        │
        └─ XOR
             ↓
        네트워크/런타임 Base ID
             │
             ├─ m_nameId
             ├─ m_describeId
             ├─ m_describe1Id
             ├─ m_groupNameId
             ├─ m_subNameId
             └─ 기타 Record 필드
```

그리고 네트워크 Bootstrap에서는:

```
protobuf
   ↓
Proto*
   ↓
OpInfo
   ↓
DataCenter Merge/Update
   ↓
UI / Game Logic
```

이 두 축을 결합하면:

```
Network ID
   ↓
Unity Record ID
   ↓
name/description/type/etc. code
   ↓
게임 UI 의미
```

까지 역매핑할 수 있다.

## 12. 다음 분석 우선순위

### 1순위 — Weapon field 39 확정

Bootstrap의 field 39 4개 entry를 직접 파싱한다.

확인할 것:

```
field39[0]
field39[1]
field39[2]
field39[3]
```

각각의 nested field가 ProtoWeapon property와 일치하는지 확인한다.

### 2순위 — Equipment protobuf field 찾기

OpInfo +0xA8 → MergeEquip 경로는 이미 확정됐으므로 protobuf 쪽에서:

```
ProtoEquipment
    field1 Id
    field2 Status
    field3 EquipmentId
    field4 HeroId
    field5 State
    field6 Level
```

형태를 만족하는 repeated field를 찾는다.

### 3순위 — Item의 BaseData 연결

MergeItem 내부에서 확인되는:

```
DataManager$$TryGetBaseData
Dictionary<int, object>
Dictionary<Int32Enum, object>
```

를 이용해:

```
ProtoItem.Id
    ↓
Item runtime
    ↓
BaseData
    ↓
Unity ItemRecord
```

를 연결한다.

이 부분이 사용자가 원하는 "네트워크 값 ↔ 코드데이터" 매핑의 핵심이다.

### 4순위 — Hero ID와 Unity 원본 연결

field37의 Hero ID와 Unity 원본 Record의 암호화 ID를 비교한다.

현재 Hero 원본 Record 파일명은 추가 탐색이 필요하므로 파일 목록에서 실제 Hero/Role 계열 Record를 찾은 뒤 연결한다.

## 13. 이번 분석에서 폐기할 가정

### 폐기 1 — protobuf field 번호와 OpInfo offset 동일시

계속 금지:

```
+0x98 → field 98
+0xA0 → field 100
```

실제:

```
OpInfo +0x98 → protobuf field 21
OpInfo +0x90 → protobuf field 37
```

처럼 완전히 별개의 번호 체계다.

### 폐기 2 — field 44 = Equipment

현재 packet 338/343의 field 44 nested 구조가 ProtoEquipment와 일치하지 않으므로 폐기한다.

### 폐기 3 — 52000100 자체가 명칭 코드

52000100은 원본 Record의 `m_id`를 복호화한 **기본 데이터 ID**이고, 명칭/설명은 별도:

```
152000100
252000100
352000100
452000100
```

형태의 필드다.

## 14. 결론

이번 분석으로 코드데이터 역매핑은 다음 단계로 진입했다.

단순히:

```
OpInfo.Items가 있다
OpInfo.Heros가 있다
```

가 아니라:

```
OpInfo.Items
    → MergeItem

OpInfo.Heros
    → UpdateHeroInfo
    → HeroInfo.InitHero

OpInfo.Weapons
    → MergeWeapon

OpInfo.Equiments
    → MergeEquip
```

라는 실제 처리 그래프가 확보됐다.

그리고 Unity 원본에서는:

```
decoded ID = currentCryptoKey XOR hiddenValue
```

가 실증됐으며, Stigmata의:

```
52000100
→ 152000100
→ 252000100
→ 352000100
→ 452000100
```

관계도 실제 데이터로 검증됐다.

따라서 이후 분석의 핵심은 **protobuf field → Proto 객체 → Runtime 객체 → Unity Record ID → 명칭/설명/유형 코드**의 완전한 연결이다.

현재 가장 먼저 해야 할 것은 **Bootstrap field 39의 실제 nested 구조를 확보하여 ProtoWeapon을 확정하는 것**이다.
