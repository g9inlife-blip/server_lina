# 2026-10-02 221B 이후 28B KCP ACK 구조 분석_GPT자문

## 1. 결론

기존 협업 문서의 221B (C→S) → 28B (S→C) → 1400B급 S→C 데이터 순서는 실제 PCAP에서 확인된다.

여기서 28B는 암호화된 protobuf 응답이 아니다.

28B 전체가 KCP ACK 패킷이며 Application Length / Flag / IV / AES 구조를 가지지 않는다.

따라서 Bootstrap OpCode=2 응답을 구현하기 전에 서버의 최소 동작은:

221B 수신 → KCP ACK 28B 즉시 전송 → 그 다음 Application OpCode=2 응답 전송

순서가 되어야 한다.

## 2. 실제 PCAP 확인

대표 사례 frame 177:
C→S, UDP payload 221B.

구조:
Session ID 8B + KCP/application header 16B + Application Length 4B + Flag 1B + IV 16B + Ciphertext 176B = 221B.

frame 178:
S→C, UDP payload 28B.

이 패킷 직후 서버는 다시 대형 게임 데이터 fragment를 전송한다.

frame 180 이후에는 S→C 1408B급 fragment가 연속적으로 전송된다.

따라서 221B → 28B → 1400B급 데이터 순서는 정확하다.

## 3. 28B raw 구조

대표 frame 178:

a6 8a 59 3a 85 bc 54 39
52 00 1f 00
98 d8 ab f0
00 00 00 00
01 00 00 00
00 00 00 00

총 28B.

현재 프로젝트 기준으로:

| Offset | Size | 값 | 의미 |
|---:|---:|---|---|
| 0x00 | 8B | a68a593a85bc5439 | Session ID |
| 0x08 | 1B | 52 | KCP ACK command |
| 0x09 | 1B | 00 | Fragment |
| 0x0A | 2B | 001f | Window |
| 0x0C | 4B | 98d8abf0 | Timestamp |
| 0x10 | 4B | 00000000 | Sequence Number |
| 0x14 | 4B | 01000000 | UNA |
| 0x18 | 4B | 00000000 | Reserved / trailing field |

핵심은 command=0x52 ACK라는 것이다.

## 4. 221B와 ACK 관계

221B의 KCP 부분은 Session ID가 a68a593a85bc5439이고 command=0x51, sequence=0, UNA=0이다.

다음 28B ACK는 command=0x52, SN=0, UNA=1이다.

즉:

client PUSH DATA, SN=0
→ server ACK, UNA=1

관계가 정확히 맞는다.

## 5. 구현상의 의미

현재 로컬 서버가 221B를 수신하고도 client가 계속 221B를 재전송하는 현상은 application layer와 KCP layer를 분리해서 봐야 한다.

실제 서버 흐름은:

221B KCP DATA 수신
→ KCP SN 확인
→ 즉시 ACK 생성
→ 28B ACK 송신
→ application payload decrypt
→ protobuf
→ OpCode=2
→ Bootstrap response

이다.

ACK는 Bootstrap protobuf 응답과 별개의 계층이다.

## 6. 28B에는 Application Length가 없다

28B ACK에서 0x08 이후를 Application packet header로 해석하면 안 된다.

Application Length 4B, Flag 0x80, IV, AES ciphertext, protobuf가 없다.

따라서 28B ACK 자체를 decrypt하지 않는다.

암호화 대상은 221B의 application payload이고 ACK는 KCP transport control packet이다.

## 7. ACK 구조에 대한 주의점

현재 관측은:

8B Session + 16B ACK header + 4B trailing/reserved = 28B

이다.

따라서 표준 24B KCP header만 전송하는 것으로 구현하지 않는다.

마지막 4B가 항상 0인지, 다른 세션/sequence에서도 동일한지 추가 검증 대상이지만 현재 샘플에서는 0이다.

## 8. 동적 필드

ACK의 SN과 UNA는 고정값으로 보내면 안 된다.

현재 사례:

received DATA SN = 0
→ ACK SN = 0
→ UNA = 1

따라서 기본 구현은 수신 DATA sequence N에 대해 ACK SN=N, UNA=N+1 관계를 유지해야 한다.

Window는 현재 샘플에서 31이지만 항상 31이라고 고정하지 않는다.

Timestamp 역시 DATA timestamp를 그대로 복사한다고 단정하지 않는다.

## 9. Bootstrap OpCode=2와의 관계

Layer 1 KCP:

221B DATA 수신 → SN 확인 → 28B ACK 송신

Layer 2 Application:

221B → App Length 193 → Flag 0x80 → IV 16B → AES-128-CBC → 172B protobuf → field 2 = OpCode 2 후보

Layer 3 Bootstrap response:

OpCode=2 → OpInfo response 생성 → Encrypt → KCP DATA → client

즉 Bootstrap 응답 구현 전에 ACK 처리가 필수 선행 조건이다.

## 11. 현재 서버 구현 우선순위

1. 221B 수신
2. KCP Session ID 추출
3. KCP DATA command=0x51 확인
4. SN 추출
5. UNA 계산
6. 28B ACK 생성
7. ACK 송신
8. application decrypt
9. field 2=2 확인
10. Bootstrap OpInfo response 생성

## 12. 현재 확정하지 않는 항목

ACK timestamp를 고정하지 않는다.
ACK window를 항상 31로 고정하지 않는다.
trailing 4B의 의미를 임의 정의하지 않는다.
Bootstrap response protobuf 전체를 추측하지 않는다.
28B ACK를 AES/protobuf packet으로 처리하지 않는다.

## 13. 최종 결론

이번 PCAP 분석으로 28B의 정체는 KCP ACK로 보는 것이 가장 강하게 확정된다.

실제 흐름:

Client
→ 221B KCP DATA, SN=0
→ Server
→ 28B KCP ACK, CMD=0x52, SN=0, UNA=1
→ Client
→ Server가 1400B급 KCP DATA fragments 전송
→ Client

따라서 현재 다음 작업은 28B ACK 생성/송신을 먼저 확실히 하고, 그 다음 Bootstrap OpCode=2 application response를 구현하는 것으로 정리한다.
