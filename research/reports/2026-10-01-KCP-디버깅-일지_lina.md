1. **암호화 방식 확정**:

   - 남은 영역은 TransformFinalBlock
   - 복호화 결과를 MemoryStream에 기록

2. **IV는 고정 0이 아님**:
   ```
   encrypted payload
   ├─ IV: 16 bytes (데이터 앞 16바이트)
   └─ Rijndael CBC ciphertext
   ```
   - 기존 `crypto.py`의 IV=zeros 가정이 틀렸음
   - 수정: IV를 데이터에서 추출하도록 변경

3. **길이 구분 필요**:
   - UDP 패킷 길이 (221B): 네트워크 전체
   - KCP 데이터 길이: KCP 헤더 처리 후
   - DecryptUnSafe 입력 길이: IV + 암호문 실제 배열
   - AES ciphertext 길이: IV 제외, 16의 배수여야 함
   - `221 - 32 = 189` 계산만으로 AES 영역 단정 금지

## 2026-10-02 14:56 — Ghidra TryRead 실제 구현 분석 (GPT)

### 18. TryRead는 KCP 전송 함수가 아니다
`Alioth.S1.Net.KCPTube$$TryRead @ 015b08bc`의 실제 구현을 Ghidra로 분석한 결과:

```
KCPTube.TryRead
      │
      ├─ 내부 버퍼 확인
      │
      ├─ 길이/헤더 해석 (BitConverter.ToInt32)
      │
      ├─ Buffer.BlockCopy
      │
      ├─ DecryptUnSafe (@015b0d28)
      │
      ├─ 필요시 DecompressUnSafe (@015b1204)
      │
      ├─ ProtoBuf.Serializer.Deserialize<object>
      │
      └─ 성공 → return 1 / 실패 → return 0
```

**중요**: `TryRead ret=0`은 "KCP에 데이터가 없다"는 의미가 아님. 복호화/압축해제/ProtoBuf 처리까지 진행한 뒤에도 0을 반환하는 경로가 존재.

### 19. DecryptUnSafe 실패 경로
```
015b0b68
    ↓
KCPTube.get_Key
    ↓
015b0d28  Alioth.S1.Net.Tools$$DecryptUnSafe
    ↓
015b0b98  tbz w0,#0x0,0x015b0c30   ; w0 bit 0 검사
    ↓
bit 0 == 0 → 0x015b0c30 → KCPTube.set_State(..., 0) → return 0
```

### 20. 현재 실험의 의심 지점
우리가 보낸 multifrag probe가 KCP 레벨에서 재조립되더라도, TryRead가 기대하는 애플리케이션 메시지 형식과 맞아야 함:
- 버퍼에서 Int32 읽기 (길이?)
- 길이/헤더 구조 검사 (`sub w8,w0,w25` / `cmp w26,#0x1`)
- BlockCopy 후 DecryptUnSafe

### 21. 다음 추적점 (GPT 권고)
TryRead 자체가 아니라 내부 두 함수를 후킹해야 함:
- **A. DecryptUnSafe** @ 015b0d28 — w0 bit 0으로 성공/실패 판정
- **B. DecompressUnSafe** @ 015b1204 — 압축해제 조건 확인

**수정된 가설**:
```
기존: KCP fragment → 재조립 실패 → TryRead ret=0
수정: KCP 수신 → TryRead → 버퍼/길이 해석 → DecryptUnSafe → (실패 시) return 0
```

따라서 다음 실험에서는 fragment 개수나 OpCode를 건드리지 말고 **DecryptUnSafe 반환값**을 잡는 게 우선.
