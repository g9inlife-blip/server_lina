# JusticeSchool Sign() 서명 알고리즘 런타임 검증 정리

- 작성일: 2026-09-29
- 대상: `com.Alioth.JusticeSchool.cn`
- 관련 스크립트: `research/justice_hook.js`
- 관련 함수: `ProtocolGame_HttpRequest.Sign`
- 관련 암호 함수: `AliothEngine.Encrypt.MD5HashString`
- 관련 .NET 함수: `System.String.Join`
- 현재 hook 버전: v4.4

---

## 1. 작업 목적

로그인 요청에 사용되는 `ProtocolGame_HttpRequest.Sign()`의 실제 서명 생성 과정을 런타임에서 확인하고, Ghidra의 정적 분석 결과와 대조하여 서명 알고리즘을 확정한다.

이번 단계에서는 단순히 `Sign()`의 반환 결과를 보는 것이 아니라 다음 지점을 직접 후킹했다.

1. `ProtocolGame_HttpRequest.Sign(content, dict)`
2. `AliothEngine.Encrypt.MD5HashString(string)`
3. `System.Convert.ToBase64String`
4. `System.String.Join` 후보

특히 MD5 함수에 실제로 전달되는 문자열을 확보함으로써 서명 생성에 사용되는 값의 순서와 구분자를 런타임에서 검증했다.

## 4. Ghidra 정적 분석 결과

`ProtocolGame_HttpRequest.Sign`의 decompile에서 확인된 흐름은 다음과 같다.

1. `content`가 null 또는 빈 문자열이면 종료
2. dictionary가 null 또는 비어 있으면 종료
3. dictionary의 Keys를 가져온다.
4. `Enumerable.OrderBy`를 사용한다.
5. 정렬된 key를 순회한다.
6. 각 key에 대응하는 dictionary value를 가져온다.
7. value들을 List에 추가한다.
8. 마지막에 `content`를 추가한다.
9. `String.Join`으로 하나의 문자열을 만든다.
10. `AliothEngine.Encrypt.MD5HashString`을 호출한다.
11. 결과를 `dict["sign"]`에 저장한다.

Ghidra에서 확인된 주요 문자열:

```text
StringLiteral_19095 = "sign"
StringLiteral_1482  = "90f04cb7a1fa5c2f58ca19cde2a2b128"
```

구분자에 해당하는 `StringLiteral_1096`은 정적 분석만으로 문자열 값이 바로 확인되지는 않았으나, MD5 hook의 실제 입력으로 구분자가 `.`임이 런타임에서 확인되었다.

## 8. 현재 확정된 Sign() 알고리즘

현재까지의 정적 분석 + 런타임 결과를 종합하면 알고리즘은 다음과 같다.

```text
Sign(content, dict):

    keys = dict.Keys
    keys = keys sorted ascending

    values = []

    for key in keys:
        values.Add(dict[key])

    values.Add(content)

    joined = String.Join(".", values)

    sign = MD5HashString(joined)

    dict["sign"] = sign
```

의사코드로 표현하면:

```text
keys = sort(dictionary.keys)

joined =
    dictionary[keys[0]]
    + "."
    + dictionary[keys[1]]
    + "."
    + ...
    + "."
    + dictionary[keys[n]]
    + "."
    + content

sign = MD5(joined)

dictionary["sign"] = sign
```

### 핵심 규칙

- dictionary의 key 자체를 MD5에 넣지 않는다.
- key를 문자열 기준 오름차순으로 정렬한다.
- 정렬된 key의 value만 사용한다.
- value 사이의 구분자는 `.`이다.
- `content`는 모든 dictionary value 뒤에 마지막으로 추가된다.
- 최종 문자열 전체를 MD5 처리한다.
- 결과를 `sign` key에 넣는다.

## 9. 빈 문자열 처리 확인

두 번째 호출에서:

```text
method = ""
```

였기 때문에 MD5 원문에 다음과 같은 부분이 나타난다.

```text
...witchwind3.logout.google...
```

즉 `method`의 빈 value도 제거하지 않고 그대로 Join에 포함한다.

따라서:

```text
A + "." + "" + "." + B
```

형태가 실제로:

```text
A..B
```

가 된다.

이것은 실제 MD5 입력에서 확인되었다.

## 10. 이전 해석에서 수정해야 할 부분

초기에는 `Sign()` 내부의 `b__40_0` 때문에 별도의 정렬 규칙이 있을 가능성을 고려했다.

하지만 이번 런타임 결과에서는 두 호출 모두 다음 규칙이 정확히 일치한다.

```text
dictionary key
    ↓
문자열 오름차순 정렬
    ↓
정렬된 key의 value
    ↓
content
    ↓
"." Join
    ↓
MD5
```

따라서 현재 단계에서는 `b__40_0`이 일반적인 identity key selector(`x => x`)일 가능성이 매우 높다.

다만 코드 수준에서 완전히 확인하려면 다음 Ghidra 함수를 직접 확인하면 된다.

```text
ProtocolGame_HttpRequest.<>c.<Sign>b__40_0
```

## 11. String.Join hook의 현재 상태

현재 `justice_hook.js v4.3`은 다음 overload를 찾으려고 했다.

```text
System.String.Join(string, object[])
```

그러나 실제 런타임에는:

```text
System.String.Join(string, string[])
@ 0x753a587b84
```

가 존재한다.

따라서 현재 Join hook은 설치되지 않았다.

다만 MD5HashString hook에서 최종 Join 결과를 직접 확보했기 때문에, Sign 알고리즘 자체의 핵심 규칙을 확인하는 데는 문제가 없었다.

### 다음 코드 수정 대상

다음 단계에서는 Join hook을:

```text
System.String.Join(string, string[])
```

기준으로 변경한다.

현재 구현되어 있는 `readIl2cppArrayStrings`를 이용하면 string[]의 각 문자열을 직접 출력할 수 있으므로, 다음 정보를 별도로 확인할 수 있다.

```text
[JOIN_DATA]
separator = "."
item[0] = ...
item[1] = ...
...
item[n] = content
```

## 14. 결론

현재 단계에서 `ProtocolGame_HttpRequest.Sign()`의 핵심 서명 생성 규칙은 사실상 확정되었다.

```text
Dictionary
    ↓
Keys 정렬(문자열 오름차순)
    ↓
정렬된 Key의 Value 추출
    ↓
마지막에 content 추가
    ↓
String.Join(".", values)
    ↓
MD5HashString()
    ↓
dict["sign"]
```

특히 가장 중요한 것은 **MD5HashString hook으로 게임이 실제로 계산한 입력 원문을 직접 확보했다는 것**이다.

따라서 앞으로의 분석은 Sign 알고리즘 자체를 추측하는 단계가 아니라:

1. Join 배열 직접 확인
2. `b__40_0` 정적 확인
3. 로컬 MD5 독립 재현
4. 실제 HTTP 로그인 요청의 `sign`과 비교
5. 이후 로그인 req/response 분석으로 연결

순서로 진행하면 된다.

## 15. `b__40_0` ARM64 디스어셈블리 확인 — 정렬 selector 확정

Ghidra에서 다음 함수를 직접 확인했다.

```text
ProtocolGame_HttpRequest.<>c$$<Sign>b__40_0()
```

실제 ARM64 코드는 다음과 같다.

```asm
00dddb90 e0 03 01 aa     mov x0, x1
00dddb94 c0 03 5f d6     ret
```

### 15.1 명령어 의미

ARM64 호출 규약에서 이 함수의 첫 번째 인자는 `x1`, 반환값은 `x0`로 전달된다.

따라서:

```asm
mov x0, x1
ret
```

은 입력값 `x1`을 그대로 반환하는 함수다.

C/C++ 관점으로 표현하면:

```c
return x1;
```

C#의 LINQ selector 관점에서는 사실상 다음과 동일하다.

```csharp
x => x
```

### 15.2 Sign()의 OrderBy와 연결

앞서 `Sign()`에서 확인한:

```text
Enumerable.OrderBy
    ↓
ProtocolGame_HttpRequest.<>c.<Sign>b__40_0
```

호출 관계와 결합하면 실제 코드는 개념적으로 다음과 같다.

```csharp
dictionary.Keys.OrderBy(x => x)
```

즉 별도의 해시, 난수, custom comparator 또는 다른 정렬 규칙을 사용하는 것이 아니다.

**Dictionary key 자체를 selector의 입력으로 받아 그대로 반환하고 있으므로, 기본 문자열 비교를 이용한 오름차순 정렬이 적용된다.**

### 15.3 런타임 결과와 교차 검증

이 결과는 앞서 확보한 MD5 입력과 정확히 일치한다.

첫 번째 호출:

```text
dict keys:
n, d, r, v, m

sorted:
d, m, n, r, v
```

실제 MD5 입력:

```text
d-value
.
m-value
.
n-value
.
r-value
.
v-value
.
content
```

두 번째 호출:

```text
dict keys:
n, d, r, v, m, t, u, p, method, platform, p2

sorted:
d, m, method, n, p, p2, platform, r, t, u, v
```

실제 MD5 입력도 정확히 같은 순서였다.

따라서 현재는 다음 세 가지 증거가 서로 일치한다.

```text
[Ghidra Sign()]
       │
       ├─ Keys
       │
       └─ OrderBy(b__40_0)
                    │
                    ▼
             [b__40_0]
                    │
                    ▼
              return x1
                    │
                    ▼
                x => x
                    │
                    ▼
          문자열 key 오름차순
                    │
                    ▼
[Runtime MD5 input] ──────── 동일한 순서
```

### 15.4 정적 분석 상태 변경

기존 문서에서는 `b__40_0`을 다음과 같이 기록했다.

```text
미확인 / identity selector일 가능성이 높음
```

이번 Ghidra 결과로 다음과 같이 변경한다.

```text
확인 완료
```

즉 `b__40_0`에 대한 추가적인 추측은 필요하지 않다.

## 19. v4.5 — V4_POST_Login → UnityWebRequest → 실제 전송 추적

Sign 알고리즘 검증을 종료하고 실제 로그인 HTTP request로 연결하기 위해 `research/justice_hook.js`를 v4.5로 확장했다.

적용 commit:

```text
c3ecbb31b628bb66827c05a3122f37a7fab5efea
research: trace V4 login HTTP request transmission
```

startup 표시 수정 commit:

```text
c06b3b1f0cefddc865d6b29af03ec7d54816d02
research: label HTTP trace hook v4.5
```

### 19.1 추가 hook 대상

Unity의 HTTP 요청 구조에 맞춰 다음 지점을 추가했다.

```text
V4_POST_Login
    ↓
UnityWebRequest .ctor(string,string)
    ↓
SetRequestHeader(string,string)
    ↓
uploadHandler / UploadHandler.get_data
    ↓
SendWebRequest()
```

Unity 공식 문서 기준으로 `UnityWebRequest`는 URL, HTTP method, custom headers와 요청 흐름을 관리하고 `UploadHandler`가 송신 body 데이터를 담당한다. `SendWebRequest()` 호출에서 원격 서버와의 통신이 시작된다. 

### 19.2 현재 v4.5가 출력하는 값

로그인 시 다음 형태를 기대한다.

```text
========== V4_POST_Login called ==========
  app_key: ...
  content: ...
  apiName: ...
  [HTTP_TRACE] login request trace window opened (10s)

[HTTP_CREATE] UnityWebRequest #1
  url: "..."
  method: "..."
  request_ptr: ...

[HTTP_HEADER] #1 Header-Name: value
[HTTP_HEADER] #1 Header-Name: value

[HTTP_SEND] UnityWebRequest #1
  url: "..."
  method: "..."
  headers: [...]
  body_len: ...
  body_utf8: "..."
  body_hex: ...
  request_ptr: ...
[HTTP_SEND END]
```

### 19.3 중요한 구현 방식

현재는 모든 UnityWebRequest를 계속 출력하지 않는다.

`V4_POST_Login` 진입 시:

```text
loginTraceUntil = 현재시간 + 10초
```

로 추적 창을 열고, 해당 10초 동안 생성되는 UnityWebRequest와 header/send를 기록한다.

이는 로그인 요청이 `V4_POST_Login` 내부에서 즉시 생성되는 경우뿐 아니라 작은 비동기 지연이 있는 경우도 잡기 위한 것이다.

### 19.4 Send 시점 최종 snapshot

`SendWebRequest()` 진입 시점에 다음 getter를 직접 호출하여 최종 상태를 읽는다.

```text
UnityWebRequest.get_url()
UnityWebRequest.get_method()
UnityWebRequest.get_uploadHandler()
UploadHandler.get_data()
```

따라서 생성 시점의 URL만 보는 것이 아니라 실제 전송 직전의 URL/method/body를 확인할 수 있다.

body는 최대 64 KiB까지 읽고 다음 두 형태로 출력한다.

```text
body_utf8
body_hex
```

### 19.5 이번 단계의 검증 목표

실행 후 다음 관계를 확인한다.

```text
V4_POST_Login
    ↓
GetDefaultParams
    ↓
Sign
    ↓
dict["sign"] 추가
    ↓
HTTP_CREATE
    ↓
HTTP_HEADER
    ↓
HTTP_SEND
    ↓
PCAP의 동일 로그인 TCP payload
```

특히 `HTTP_SEND.body_utf8` 또는 `body_hex`에서 실제 로그인 request body를 확보하면, 앞서 확보한:

```text
content
dictionary
sign
```

이 실제 전송 데이터에 어떻게 배치되는지 직접 확인할 수 있다.

### 19.6 아직 확인하지 않은 부분

현재 v4.5는 우선 **요청 생성과 전송 직전**을 확인하는 단계다.

아직 다음은 별도 검증 대상이다.

- `UnityWebRequest` constructor가 실제 로그인 경로에서 사용되는지
- 실제 body가 `UploadHandlerRaw`를 통해 만들어지는지
- body가 UTF-8 평문인지 다른 인코딩/직렬화인지
- response body와 response code
- PCAP의 TCP payload와 HTTP request body의 정확한 대응
- UnityWebRequest가 아닌 별도 HTTP/native networking 경로를 사용하는 요청이 있는지

따라서 v4.5 첫 실행에서 `[HTTP_CREATE]`가 나오지 않더라도 hook 실패로 단정하지 않는다. 그 경우 다음 단계에서는 실제 사용된 다른 `UnityWebRequest` 생성 overload 또는 정적 `UnityWebRequest.Post/Put` 경로를 추가 추적한다.

### 19.7 다음 실행 방법

기존과 동일하게 게임 프로세스에 v4.5를 attach한 뒤 로그인한다.

확인할 핵심 로그는:

```text

[HTTP_CREATE]
[HTTP_HEADER]
[HTTP_SEND]
```

이다.

첫 실행 결과를 기준으로 다음 단계는 실제 사용된 request 생성 overload와 body 구성 함수를 좁히고, 같은 시점의 PCAP과 1:1 대조한다.

## 20. v4.6 — 실제 POST body 생성 지점 추적 준비

### 20.1 추가한 hook

UploadHandlerRaw(byte[])
UnityWebRequest.set_uploadHandler(UploadHandler)
UnityWebRequest.set_method(string)

## 24. 로그인 이후 인게임 정보가 아직 보이지 않는 이유

현재 hook에서 확인된 것은 V4 로그인 HTTP 경로와 로그인 직후 10초간의 UnityWebRequest다.

실행 결과에는 로그인 외에 AssetBundle 요청도 잡혔다. 따라서 현재 단계에서 로그인 HTTP부터 메인 화면과 인게임 데이터 요청까지 전체가 모두 추적되었다고 볼 수는 없다.

다음 단계에서 로그인 body를 먼저 확정한 뒤, AliothEngine.Net.HttpRequest, UnityWebRequest, native TCP / KCPTube 중 실제 인게임 정보 요청이 사용하는 경로를 찾아야 한다.

특히 기존 PCAP/DH64 분석에서 확인한 KCPTube/TCP 계열 통신이 실제 게임 데이터 채널이라면, 인게임 정보가 UnityWebRequest 로그에 나타나지 않는 것이 가능하다.

따라서 로그인 HTTP 분석과 인게임 TCP/DH64 분석을 연결하는 단계로 넘어간다.

## 25. v4.6 실제 런타임 결과 — ARM64 실기기에서 로그인 body 확보

이번 검증은 **LDPlayer/x86 에뮬레이터가 아니라 ARM64 실기기에서 hook-patched APK를 실행한 결과**다.

x86 에뮬레이터에서는 현재 hook 환경이 동작하지 않으므로 이후 문서와 실행 절차에서도 LDPlayer를 전제로 하지 않는다.

### 25.1 런타임 method inventory

v4.6에서 다음 Unity HTTP 경로가 실제 런타임에서 확인되었다.

```text
UnityEngine.Networking.UnityWebRequest.get_url()
UnityEngine.Networking.UnityWebRequest.get_uploadHandler()
UnityEngine.Networking.UnityWebRequest..ctor(System.String, System.String)
UnityEngine.Networking.UnityWebRequest.SetRequestHeader(System.String, System.String)
UnityEngine.Networking.UploadHandlerRaw..ctor(System.Byte[])
UnityEngine.Networking.UnityWebRequest.set_uploadHandler(UnityEngine.Networking.UploadHandler)
UnityEngine.Networking.UnityWebRequest.set_method(System.String)
UnityEngine.Networking.UnityWebRequest.SendWebRequest()
```

또한 `AliothEngine.Net.HttpRequest`의 주요 request 구성 메서드가 확인되었다.

```text
.ctor(...)
AddHeader(string,string)
AddData(string,string)
AddRangeData(Dictionary<string,string>)
AddBinaryData(...)
Request()
CreateURL(List<string>, string, Dictionary<string,string>)
```

따라서 다음 정적 분석은 `AddData → AddRangeData → Request → CreateURL` 순서로 진행한다.

## 26. Ghidra Listing 자료 추가 및 분석 전략

`research/Ghidra_Listing_txt`에는 Ghidra Listing 결과가 함수명 시작 문자열 기준으로 묶여 압축되어 있다.

예:

```text
AB.zip
AC.zip
AD.zip
...
XL.zip
...
ZH.zip
FUN_.zip
```

`FUN_.zip`은 사용자가 별도 스크립트로 함수명이 자동 명명되지 않은 `FUN_*` 함수만 분리한 자료다.

따라서 앞으로 Ghidra 정적 분석은 전체 Listing을 무작정 순회하지 않고 다음 우선순위로 수행한다.

1. 현재 runtime에서 확인된 `AliothEngine.Net.HttpRequest` 함수 주소와 이름을 Listing에서 역추적
2. `AddData`
3. `AddRangeData`
4. `Request`
5. `CreateURL`
6. 관련 `.ctor`
7. body URL-encoding / form serialization 함수
8. `FUN_.zip`에서 위 함수가 호출하는 미명명 helper 확인
9. 이후 로그인 response 처리 함수
10. 로그인 이후 실제 게임 TCP/KCP/DH64 경로 연결

특히 `FUN_.zip`은 단순 미사용 함수 모음이 아니라, 현재 이름이 없어 직접 검색하기 어려운 helper를 찾는 보조 자료로 사용한다.

### 26.1 정적/동적 분석 연결 기준

앞으로 함수 후보는 다음 세 종류의 증거를 함께 사용한다.

```text
[Ghidra Listing]
    함수명 / 주소 / 호출관계 / 문자열 / 상수
             +
[Runtime Hook]
    실제 호출 / 인자 / 반환값 / 객체 상태
             +
[PCAP]
    실제 전송 bytes / URL / TCP stream
```

세 자료가 같은 흐름을 가리키는 경우에만 함수 역할을 확정한다.

### 26.2 다음 정적 분석 목표

현재 가장 중요한 것은 `Sign()` 자체가 아니라 **551-byte 로그인 body가 어떻게 만들어졌는지**다.

따라서 Ghidra에서 다음 흐름을 우선 확인한다.

```text
AliothEngine.Net.HttpRequest.AddData
        ↓
AddRangeData
        ↓
CreateURL / request data serialization
        ↓
Request
        ↓
UnityWebRequest
        ↓
UploadHandlerRaw(byte[])
```

이 분석이 끝나면 로그인 request 생성 규칙을 코드 수준에서도 설명할 수 있고, 이후 동일 구조를 사용하는 다른 API 요청을 찾기 쉬워진다.
