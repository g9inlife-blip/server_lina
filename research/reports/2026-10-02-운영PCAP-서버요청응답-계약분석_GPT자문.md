# 2026-10-02 운영 PCAP 기반 서버 요청/응답 계약 분석_GPT자문

## 1. 이번 문서의 목적

기존 2026-10-01-메인화면-응답-Chapter-런타임추적-후속_GPT자문.md는 메인화면 Bootstrap과 Chapter/창고 데이터가 Client 내부에서 어떻게 연결되는지를 런타임/Ghidra 중심으로 추적했다.

이번 문서는 그 분석과 별도로, 실제 운영 서버에서 발생한 PCAP/JSON을 기준으로 Local Server가 어떤 요청을 받고 어떤 Response를 만들어야 하는지 정리한다.

핵심 원칙:

~~~
운영 PCAP/JSON
    ↓
실제 Client → Server request
    ↓
실제 Server → Client response
    ↓
protobuf field/값 비교
    ↓
서버 계약(contract) 작성
    ↓
Local Server 구현

Ghidra
    ↓
PCAP에서 의미가 불명확한 field/opcode/dispatch를 보조 확인
~~~

즉 이번 방향에서는 Ghidra에서 서버 요청을 추측하지 않는다. 실제 운영 패킷을 우선하며, Ghidra는 패킷만으로 확정할 수 없는 내부 의미를 보완하는 용도로 사용한다.

## 3. 현재 운영 기준으로 가장 중요한 확정 사례 — 0x14

기존 운영 PCAP 분석에서 다음 요청/응답이 확인됐다.

### frame 428 — Client → Server

~~~
opcode     = 0x14
chapterId  = 20000100
boxIndex   = 5
~~~

### frame 430 — Server → Client

~~~
opcode(field #2) = 0x14
flag             = 0x84
application      = 353 bytes
plaintext        = 329 bytes
~~~

이는 추측한 요청 형식이 아니라 실제 운영 서버와 Client 사이에서 발생한 요청/응답 쌍이다.

따라서 Local Server에서 0x14를 구현할 경우 이 frame pair를 기준 샘플로 사용해야 한다.

## 4. frame 430의 실제 Response 구조

기존 분석에서 frame 430의 plaintext 내부에 다음 구조가 확인됐다.

~~~
field 43
 └─ length 30
    ├─ field 1  = 20000100
    ├─ field 3  = 6
    ├─ field 4  = 1
    ├─ field 9  = { field1=1, field2=15 }
    ├─ field10  = { field1=1, field2=15 }
    └─ field11  = 1
~~~

Ghidra에서 확인된 ProtoChapter 메모리 구조:

~~~
+0x10 = Id
+0x14 = Status
+0x18 = Progress
+0x1C = BoxStatus
~~~

내부 함수:

~~~
IsBoxReceived(mask)
    = (BoxStatus & mask) != 0

mask = 1 << boxIndex
~~~

현재 확정된 사실:

- Chapter 객체에 Id/Status/Progress/BoxStatus가 존재한다.
- Box 상태는 bitmask 방식이다.
- Box UI index i의 상태 검사 mask는 1 << i이다.
- frame 428의 boxIndex=5라면 UI 코드 기준 mask는 0x20이다.
- BoxStatus의 구조 자체는 운영/런타임 분석에서 별도로 검증 완료된 것으로 취급한다.
- 따라서 이번 문서에서는 BoxStatus 자체를 UNKNOWN/PROVISIONAL로 낮추지 않는다.
- 다만 frame 430의 특정 nested field가 BoxStatus의 어느 protobuf field에 정확히 대응하는지는 별도 field-level 매핑 문제이므로, 그 부분은 실제 bytes와 반복 PCAP을 기준으로 구분한다.

즉 **BoxStatus 구조는 확정**하고, 필요한 경우 protobuf field 번호와의 1:1 대응만 추가 검증한다.

## 5. 0x14 Response에서 현재 확정 가능한 계약

현재 서버 구현 관점에서는 다음 수준까지 사용할 수 있다.

### Request

~~~
Operation = 0x14

Request:
    chapterId = 20000100
    boxIndex  = 5
~~~

### Response

~~~
Operation = 0x14
Return/response payload:
    Chapter snapshot 포함
    Chapter.Id = 20000100
    기타 Chapter 상태 field 존재
~~~

Response 전체 329B protobuf는 이미 운영 패킷에서 확보되어 있으므로, 서버 구현 시 임의의 새로운 protobuf를 만드는 것보다 해당 실제 Response를 기준으로 field 구조를 재현하는 방식이 우선이다.

## 6. 기존 메인화면 런타임 분석과의 연결

기존 운영기준 분석에서는 Login Bootstrap도 실제 runtime에서 다음 경로로 확인됐다.

~~~
KCPTube.Send

    ↓
OpCode=2
    ↓
KCPTube.TryRead
    ↓
Deserialize<object>
    ↓
NetworkCenter.TryHandleResponse
    ↓
DataCenter.ProccessRequestRes
    ↓

~~~

Bootstrap Response의 OpInfo에는 다음 상태가 실제 존재했다.

~~~

Weapons
Equiments
Chapters
Sections
Teams
ViewItems
Fashions
Quests
Shops
Charges
Friends
Exam

~~~

또한:

~~~

    ↓

    ↓

~~~

가 runtime에서 확인됐다.

따라서 서버 구현은 다음 두 종류의 계약으로 나누는 것이 좋다.

~~~

~~~

이 둘을 하나의 거대한 Response로 추측해서 구현하지 않는다.

## 7. 중요한 관점 변경 — 요청을 Ghidra에서 찾는 것이 아님

잘못된 접근:

~~~
Ghidra
 ↓
어떤 함수가 서버 요청일 것이라고 추측
 ↓
protobuf 구조 추정
 ↓
Local Server 구현
~~~

권장 접근:

~~~
운영 PCAP
 ↓
Client → Server packet 확인
 ↓
opcode 확인
 ↓
request protobuf 추출
 ↓
Server → Client response 확인
 ↓
response protobuf 추출
 ↓
동일 opcode의 다른 사례 비교
 ↓
필드 의미 확정
 ↓
Ghidra로 내부 객체/dispatch와 대조
 ↓
Local Server 구현
~~~

Ghidra는 마지막 단계의 검증 도구가 된다.

## 8. 운영 PCAP에서 앞으로 우선 추출해야 하는 것

현재 repository에는 행동별 PCAP/JSON이 충분히 있다.

### 1순위 — 이미 양방향이 확정된 0x14

~~~
frame 428 C→S
frame 430 S→C
~~~

해야 할 작업:

- Request 전체 plaintext hex
- Request protobuf field tree
- Response 전체 plaintext hex
- Response protobuf field tree
- session/serial/opcode 상관관계
- 동일 chapterId의 다른 frame 검색
- 다른 boxIndex 사례 검색

이 작업이 끝나면 0x14는 서버 구현에 직접 넘길 수 있는 계약이 된다.

### 2순위 — Bootstrap OpCode=2

운영 PCAP과 runtime을 함께 비교한다.

확인할 것:

- Request 전체 구조
- Response 전체 protobuf
- User 최소 필드
- Items 최소 필드
- Heros 최소 필드
- Chapters 최소 필드
- Main 진입 직후 Client가 실제 접근하는 필드

목표는 전체 OpInfo를 재현하는 것이 아니라 Main 진입에 필요한 최소 Response를 찾는 것이다.

### 3순위 — 던전/전투

이미 다음 행동을 포함한 운영 PCAP이 있다.

~~~
챕터 선택
→ 전투
→ 승리
→ 보상
~~~

여기서 Request opcode, Response opcode, request parameter, response state를 추출한다.

### 4순위 — Box 외 장비/제작/강화

이미 다음 운영 캡처가 있다.

~~~
장비조각
→ 장비제작
→ merge
→ 장비착용
~~~

이 자료는 향후 DataCenter Merge 계열과 실제 서버 response를 연결하는 데 사용할 수 있다.

## 9. 동일 행동을 여러 PCAP에서 비교해야 하는 이유

단일 패킷 하나만 보면 protobuf field 번호와 내부 객체 field를 잘못 1:1 대응할 가능성이 높다.

단, BoxStatus 구조 자체는 이미 별도 검증된 사실이며, 여기서 비교해야 하는 것은 BoxStatus의 존재 여부가 아니라 **어느 protobuf field가 그 상태를 전달하는지와 각 bit의 의미**이다.

현재 Box 사례:

~~~
boxIndex = 5
mask = 1 << 5 = 0x20
response nested field 4 = 1
~~~

만 보면 field 4를 BoxStatus라고 해석하고 싶어진다.

그러나 값이 1이므로 mask 0x20과 맞지 않는다.

따라서 현재처럼 field 4 = BoxStatus를 바로 확정하지 않고 다음을 비교해야 한다.

~~~
PCAP A
    boxIndex=5

PCAP B
    boxIndex=0/1/2/...

PCAP C
    동일 chapter의 Box 오픈 전 상태

PCAP D
    동일 chapter의 Box 오픈 후 상태
~~~

같은 field의 값이 행동에 따라 어떻게 변하는지가 이름보다 강한 증거다.

## 10. 서버 구현에서 지켜야 할 기준

Local Server 구현에 넘길 계약은 다음 등급으로 관리한다.

### CONFIRMED

다음 증거가 있으면 확정:

- 실제 운영 PCAP의 request/response
- 반복 관측
- runtime 값과 일치
- Ghidra 내부 field offset과 일치

### STRONG

다음 중 2개 이상이 일치하지만 직접적인 반복 검증이 부족한 경우:

- PCAP 구조
- runtime 구조
- Ghidra 구조

### PROVISIONAL

현재 한 번의 패킷이나 정적 분석으로만 추정한 경우.

### UNKNOWN

현재 정보로 의미를 결정할 수 없는 field.

서버 구현에 바로 넣어도 되는 것은 기본적으로 CONFIRMED이며, STRONG은 구현 후 실제 Client 동작으로 검증한다.

PROVISIONAL/UNKNOWN은 임의의 의미를 부여하지 않는다.

## 11. 221B/DH 분석과의 관계

2026-10-02 별도 자문에서 221B RAW 구조와 DH session key pairing도 실제 runtime 로그로 검증됐다.

현재 확인된 application packet 구조:

~~~
[Session ID 8B]
[Transport/KCP header 16B]
[Application Length 4B]
[Flag 1B]
[IV 16B]
[AES-128-CBC ciphertext]
~~~

그리고 현재 서버의 33B handshake response 순서와 Client의 DH 읽기 순서를 비교했을 때 실제 session key는 cross pairing으로 복호화되는 것이 확인됐다.

이 부분은 패킷 운반/복호화 계층의 계약이고, 이번 문서의 0x14/OpCode 계약은 그 위의 protobuf application 계층 계약이다.

따라서 구현을 다음 계층으로 분리한다.

~~~
KCP / DH / AES
        ↓
Application packet
        ↓
Protobuf
        ↓
OperationCode
        ↓
Request handler
        ↓
Response protobuf
~~~

어느 한 계층의 문제를 다른 계층의 문제로 해석하지 않는다.

## 12. 이번 단계의 서버 구현 방향

현재 Local Server가 먼저 가져야 할 것은 전체 게임 서버가 아니다.

최소한 다음 구조가 필요하다.

~~~
KCP receive
    ↓
DH/AES decrypt
    ↓
protobuf decode
    ↓
OpCode dispatch
    ↓
state lookup/update
    ↓
protobuf response
    ↓
AES encrypt
    ↓
KCP send
~~~

application handler는 최소한:

~~~
OpCode 2
    → Bootstrap Response

OpCode 0x14
    → Chapter/Box Response
~~~

부터 실제 운영 패킷과 동일하게 만든다.

그 이후 던전, 보상, 장비, 제작, 강화 등을 실제 PCAP 순서대로 추가한다.

## 14. 현재 결론

이번 분석에서 가장 중요한 결론은 다음과 같다.

운영 PCAP/JSON을 이미 충분히 확보하고 있으므로, 서버 요청을 만들기 위한 1차 자료는 Ghidra가 아니라 운영 패킷이다.

특히 현재는:

~~~
실제 운영

frame 428
Client → Server
OpCode 0x14
chapterId 20000100
boxIndex 5

        ↓

frame 430
Server → Client
OpCode 0x14
329B protobuf response
Chapter snapshot 포함
~~~

이라는 완전한 request/response 사례가 존재한다.

따라서 다음 단계에서는 Ghidra에서 새로운 요청 구조를 추측하지 않고 frame 428/430의 실제 plaintext protobuf를 기준으로 서버 Response를 재현하는 것이 가장 우선이다.

기존 2026-10-01 메인화면 런타임 분석은 이 작업을 보완한다.

~~~
운영 PCAP
    ↓
실제 wire contract

Ghidra
    ↓
class / field / dispatch 의미 검증

Runtime
    ↓
Client가 실제 사용하는 필드 검증

Local Server
    ↓
검증된 contract 구현
~~~

이 순서로 진행한다.
