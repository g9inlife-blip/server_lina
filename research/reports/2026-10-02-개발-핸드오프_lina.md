## 3. 프로토콜 상세

### 3.1 핸드셰이크
```
C→S: 368B = [24B 헤더][344B 토큰]
S→C: 33B = [Session 8B][0x11][srv_pub2 8B][0x19][srv_pub1 8B]
```
- DH 크로스 페어링:
  - `secret1 = client_pub1 ^ server_private2`
  - `secret2 = client_pub2 ^ server_private1`
  - `session_key = LE64(secret1) || LE64(secret2)` (16B)

### 3.2 221B (C→S 로그인 요청)
```
[Session 8B][Header 16B][App Length 4B=193][Flag 1B=0x80][IV 16B][Ciphertext 176B]
```
- 복호화 후 172B protobuf:
  - field 1 (varint): SerialNumber
  - field 2 (varint): OpCode (2 = Bootstrap)
  - field 4,5,12,13,14,15: 디바이스 정보

### 3.3 28B ACK (S→C)
```
[Session 8B][0x52][0x00][0x1f 0x00][Timestamp 4B][SN 4B][UNA 4B][Reserved 4B]
```
- `0x52` = ACK CMD, Window raw `1f 00` = LE uint16 31
- SN = 수신한 DATA의 SN, UNA = 누적 확인 번호

### 3.4 S→C Fragment (서버 → 클라이언트)
```
[Session 8B][KCP 16B][ChunkLen 4B][chunk]
KCP 16B = [CMD 1B=0x51][FRG 1B][WND 2B=32][TS 4B][SN 4B][UNA 4B]
chunk 연결 = [Flag 1B][IV 16B][Ciphertext]
```
- SN=0..N, FRG=N..0 (내림차순)
- chunk ≤ 1372B, UDP ≤ 1400B

## 4. 클라이언트 처리 파이프라인 (Ghidra 분석)

### 4.1 KCPTube.TryRead @ 015b08bc
단순 KCP 수신 함수가 아니라 전체 파이프라인:
```
KCP 데이터 수신
  ↓
메시지 길이/버퍼 처리 (BitConverter.ToInt32)
  ↓
Buffer.BlockCopy
  ↓
DecryptUnSafe @ 015b0d28
  ↓ (실패 시 set_State(0) → return 0)
필요시 DecompressUnSafe @ 015b1204
  ↓
ProtoBuf.Serializer.Deserialize<object>
  ↓
성공 → return 1 / 실패 → return 0
```

**중요**: `ret=0`은 "데이터 없음"이 아니라 복호화/압축해제/역직렬화 실패를 포함한 모든 실패를 의미. `ret=0`만으로 "태그가 틀렸다"고 단정할 수 없음.

### 4.2 Frida 체크포인트
`research/frida/justice_hook_opinfo.js`의 후킹 지점:
```
[LOGIN_GS] LoginManager.LoginGameServer
  ↓
[KCP_RX] KCPTube.TryRead ENTER/LEAVE (ret=0 또는 1)
  ↓
[RESP] NetworkCenter.TryHandleResponse ENTER/LEAVE
  ↓
[BOOT_RESP] DataCenter.ProccessRequestRes (OpCode 출력)
  ↓
[BOOT_STATE] OpInfo 20개 필드의 null/non-null 출력
```

**판정 기준**:
- KCP_RX 없음 → KCP reassembly 이전 문제
- KCP_RX 있음 (ret=0 반복) → Decrypt/Decompress/Deserialize 중 실패
- KCP_RX ret=1 → 파싱 성공
- RESP 없음 → response dispatch 문제
- BOOT_RESP 없음 → DataCenter 라우팅 문제
- BOOT_STATE 비어있음 → OpInfo 필드가 모두 null (데이터 없음)

## 5. PROBE_MODE 설명

`app/kcp/server_udp.py`의 `PROBE_MODE` 변수로 서버 응답 모드 전환:

| 모드 | 설명 | 상태 |
|------|------|------|
| `simple` | field 1+2만 (7B) | 미사용 |
| `multifrag` | field 1+2 반복 ~16KB, 12 fragments | ✅ ret=1 확인됨 (2026-10-02 15:07) |
| `multifrag_tag` | field 3~64 추가 (태그 추측, 폐기됨) | ❌ 전부 ret=0, 폐기 |

| `replay` | 000192_s2c.bin 원본을 우리 키로 재암호화 | 🔄 테스트 대기 중 (2026-10-02 16:00) |

**환경변수**:
- `TAG_RANGE="3-20"` : multifrag_tag에서 태그 구간 지정 (현재 미사용)

## 6. 실패한 가설들 (반복하지 말 것)

### 6.1 "protobuf 파서 사망설" (폐기)
- multifrag_tag 후 클라이언트가 ACK도 안 보낸다고 추측했으나, 실제로는 KCP 세그먼트 자체를 거부한 것이었음.
- 13:27에 multifrag로 transport 개통 확인되면서 폐기.

### 6.2 "Frida가 KCP를 막는다" (폐기)
- GPT 운영 스크립트에서 Frida+KCP 정상 동작 확인.
- 우리가 잘못된 메서드(`CSBehaviour.Connect`)를 후킹하고 있었음.
- 실제 네임스페이스: `Alioth.S1.Common.OpInfo`, `Alioth.S1.Net.KCPTube`.

### 6.3 "태그 3~64 추측" (폐기)
- 메모리 오프셋(+0x88 등)이 protobuf 태그라고 가정했으나 틀렸음.
- 실제 태그는 21, 35, 37, 38, 39, 40, 43, 44, 45, 48, 49, 51, 56.
- 3개 구간(3-20, 21-40, 41-64) 모두 ret=0으로 실패.

### 6.4 "캐시 문제" (사용자가 반박)
- 리다이렉트 실패 시 내가 캐시 문제라고 추측했으나, 사용자의 지적("js를 수정해야하는거 아니야?")이 맞았음.
- 실제 원인은 내 JS 어댑테이션 버그.

**출처**: `research/reports/2026-10-02-Bootstrap-OpCode2-응답계약-검증-메인화면진입-성공-후속_GPT자문.md`

### 11.1 1차 마일스톤 확정 (091aeea3)
Replay로 메인 화면 진입 성공. 다음이 실증됨:
1. Request Serial을 Response에 반영하는 것이 정상 동작한다.
2. 운영 Bootstrap gzip을 수정 후 재압축해도 Client가 정상 처리한다 (13290B→13325B).
3. KCP fragment 개수가 운영 데이터와 달라도 정상 처리할 수 있다 (10개).
4. 현재 Session Key를 이용한 encryption pipeline이 정상 동작한다.
5. Client의 TryRead → Deserialize → Bootstrap 처리 → Main 진입이 연결된다.

### 11.2 우선순위 낮아진 영역
- KCP 기본 송수신, AES/세션키, gzip byte 동일성, fragment 개수 고정, 최소 Probe transport 문제.

### 11.3 다음 목표: 자체 Bootstrap Builder
```
[현재] 운영 Bootstrap 데이터 → Serial patch → Main
[다음] 자체 생성 Bootstrap protobuf → gzip → encrypt → KCP → Main
```

### 11.4 전환 전략
- **단계 A**: 성공 Replay를 GOLDEN BASELINE으로 보존 (회귀 테스트).
- **단계 B**: protobuf payload만 교체 (KCP/암호화/압축 파이프라인 유지).
- **단계 C**: 자체 protobuf를 gzip으로 압축.
- **단계 D**: 기존 pipeline 재사용.

### 11.5 핵심 원칙
- C# 메모리 오프셋(+0x88 등)과 protobuf 필드 번호를 절대 동일시하지 않는다.
- 실험은 한 번에 하나의 계층만 변경한다.
- 실패 시 문제 범위를 protobuf builder로 좁힐 수 있어야 한다.

### 11.6 2차 마일스톤

### 12.2 Gold 위치 발견
- 사용자가 "35025가 금화 수량인데 안 바뀐다"고 보고
- 실측 protobuf에서 35025 varint 검색 → **1개 위치 발견**:
  ```
  root/field 38/f2/field 3 = 35025
  ```
- **field 38 = currency 목록**, 각 entry = {f1=currency ID, f2={f1=ID, f3=amount}}
- **Gold = currency ID 43000001, f3 (amount) = 35025**
- field 35.User.field 7 (18100000)은 gold가 아님 → 원상복구

### 12.3 Surgical Patch 전략
- Builder(빈 데이터) 대신 **Replay + surgical patch**로 전환
- 실측 데이터 전체 사용 + gold (field 38.currency[43000001].f3)만 999999로 변경
