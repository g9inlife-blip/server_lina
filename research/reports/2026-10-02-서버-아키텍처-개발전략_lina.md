## 2. 클라이언트 처리 파이프라인 (확정)

```
HTTP Login
   ↓
LoginManager.LoginGameServer
   ↓
UDP 8000
   ↓
DH/Session Handshake (368B → 33B)
   ↓
KCP (221B → 28B ACK)
   ↓
KCPTube.TryRead @ 015b08bc
   ├─ 내부 버퍼 확인
   ├─ 길이/헤더 해석 (BitConverter.ToInt32)
   ├─ Buffer.BlockCopy
   ├─ DecryptUnSafe @ 015b0d28
   ├─ 필요시 DecompressUnSafe @ 015b1204
   ├─ ProtoBuf.Serializer.Deserialize<object>
   └─ 성공 → return 1 / 실패 → return 0
   ↓
NetworkCenter.TryHandleResponse
   ↓
DataCenter.ProccessRequestRes
   ↓
OpInfo / UserInfo / HeroInfo / Items / Chapters ...
   ↓
Unity UI
```

**중요**: `TryRead ret=0`은 "KCP에 데이터가 없다"는 의미가 아니다. 복호화/압축해제/ProtoBuf 처리까지 진행한 뒤에도 0을 반환하는 경로가 존재한다.

## 6. 개발 우선순위

### ① KCP Session 정상화 (현재 최우선)
```
UDP → Handshake → DH → Session Key → 221B 정상 해석
```
- 상태: 221B 복호화까지는 성공. S→C 암호화가 문제.

### ② KCP → TryRead 성공시키기
**목표는 딱 하나**:
```
[KCP_RX] TryRead ENTER
[KCP_RX] TryRead LEAVE ret=1
[RESP] TryHandleResponse ENTER
```
그 다음에 `[BOOT_RESP]`가 나오는지를 본다.

### ③ 정상 Deserialize 확인
```
TryRead → Decrypt → Decompress → Deserialize → OpCode=2
```
이것을 먼저 확정한다.

### ④ Bootstrap Response 구현
```
OpCode=2 → ReturnCode=0 → OpInfo → User/Heros/Items/Weapons/Equiments/Chapters/...
```
여기에는 현재까지 확보한 계약을 넣는다.

### ⑤ Main 화면 완성 (1차 마일스톤)
```
Login → KCP → Bootstrap → Main
```

### ⑥ Warehouse/Chapter로 확장 (2차)
화면 단위로 하나씩 완성:
- Warehouse 클릭 → Request → Opcode → Response → Warehouse 표시
- Chapter 클릭 → Request → Opcode → Response → Chapter UI

## 8. 리나의 분석

### 8.1 왜 Decrypt가 실패하는가?

현재 가설:
1. **S→C 암호화 키가 C→S와 다를 수 있음**: 221B 복호화는 성공했으니 C→S 키는 맞다. 하지만 S→C는 다른 키를 쓸 수 있다.
2. **Flag 문제**: 우리는 0x84를 쓰는데, 실제 서버는 0xc4를 쓴다. 0x40 비트가 압축을 의미한다면, 클라이언트는 0xc4를 보고 Decompress를 시도할 것이다. 우리가 0x84로 보내면 Decompress를 건너뛰는데, 만약 클라이언트가 0x84를 잘못 해석하면 문제가 된다.
3. **메시지 형식 문제**: TryRead는 버퍼에서 Int32를 읽어 길이를 확인한다. 우리의 probe 형식이 이 기대와 맞지 않을 수 있다.

### 8.2 가장 빠른 검증 방법

`DecryptUnSafe @ 015b0d28`를 후킹해서 w0 bit 0을 확인하면, 복호화 실패인지 다른 문제인지 바로 판정할 수 있다.

하지만 사용자가 "아니"라고 했으므로, Frida 후크 추가는 보류한다.

### 8.3 대안: 서버 측에서 검증

서버가 보낸 데이터를 **서버 자신이 복호화**해서 검증할 수 있다:
1. 서버가 probe를 암호화한다.
2. 서버가 같은 키로 복호화를 시도한다.
3. 복호화가 성공하면 키/IV/형식은 맞는 것이다.
4. 그래도 클라이언트가 실패하면, 문제는 클라이언트 측 기대 형식이다.

이건 Frida 없이 서버만으로 할 수 있는 자가검증이다.

### 8.4 Flag 0x84 vs 0xC4 실험

현재 서버 코드 주석: `# flag 0x84 (0xc4는 압축 의미일 수 있어 비압축인 우리는 0x84)`

실험 제안:
- 실험 A: flag 0x84로 전송 (현재) → 결과 기록
- 실험 B: flag 0xC4로 전송 (실측과 동일) → 결과 기록
- 단, 0xC4로 보낼 때는 데이터를 실제로 압축해야 할 수도 있다.

Ghidra에서 DecompressUnSafe의 호출 조건을 확인하면, 0x40 비트가 압축을 의미하는지 확정할 수 있다.

## 10. GPT 정상 응답 기준 분석 (2026-10-02 15:39)

### 10.1 핵심 방향
전체 구조를 더 분석하는 것보다 **정상 응답과 로컬 응답의 차이를 좁히는 작업**이 중요.

운영 서버의 데이터를 추측해서 만드는 게 아니라, 기존에 확보한 정상 통신 자료를 기준으로 로컬 응답을 검증.

### 10.2 테스트 결과 해석

| 테스트 | 결과 | 해석 |
|--------|------|------|
| field 1+2 | ret=1, BOOT_RESP 후 크래시 | 파싱은 통과, 후속 처리에서 실패 |
| field 3~20 | ret=0 | 추가 필드 중 잘못된 데이터 존재 가능 |
| field 21~40 | ret=0 | 동일 |
| field 41~64 | ret=0 | 동일 |

**주의**: Protobuf는 같은 필드의 반복을 허용하는 경우가 많음. 반복 자체가 반드시 오류는 아님. 필드 번호뿐 아니라 wire type, 값의 인코딩, 중첩 메시지 구조가 중요.

### 10.3 권고 해결 방법

**1. 정상 PCAP에서 Bootstrap 응답 확보**
- field 번호, wire type, 값의 원시 바이트, 중첩 메시지 내부 필드, 반복 필드 개수, 필드별 등장 순서 추출.
- 이것이 로컬 서버가 따라야 할 실제 기준.

**2. field를 하나씩 검증**
- 3~20, 21~40처럼 나누면 여러 문제가 섞여서 원인 파악 어려움.
- field 1+2 → field 3 하나 추가 → 확인 → field 4 추가 → 반복.
- 실패하는 필드를 찾으면 해당 필드의 wire type과 내부 구조를 정상 PCAP과 대조.

**3. Deserialize와 Bootstrap 처리 분리 테스트**
- 단계 A (직렬화/역직렬화): 파싱 성공 여부, 필드 타입, 중첩 메시지, 반복 필드.
- 단계 B (Bootstrap 데이터 처리): UserInfo 생성, Items/Heros/Chapters 병합, 메인 UI 초기화.
- 두 단계를 분리해야 ret=1 이후 크래시 원인도 파악 가능.
