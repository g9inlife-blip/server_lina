## 28B ACK Window 바이트 순서 버그 수정 (2026-10-02 12:35)

### 증상
28B ACK을 전송해도 클라이언트가 221B를 계속 재전송 (동일 평문, 헤더 timestamp만 변경).

### 원인
GPT 자문 문서의 28B raw 바이트:
```
52 00 1f 00 | 98 d8 ab f0 | 00 00 00 00 | 01 00 00 00 | 00 00 00 00
```
Window raw 바이트는 `1f 00` = LE uint16 → **31**.
구현에서 `struct.pack_into("<H", ack, 0x0A, 0x1F00)`으로 pack → raw `00 1f`가 되어 실제 서버와 다름.
클라이언트가 이 ACK을 유효하지 않다고 보고 재전송을 멈추지 않음.

### 수정
`app/kcp/server_udp.py`: `0x1F00` → `31` (raw `1f 00`, 실제 서버와 동일).
- Window=31은 현재 관측 샘플 기준. GPT 자문대로 항상 31로 고정하지는 않음 (추후 동적 처리 검토).

### 다음 검증
1. `git pull` 후 UDP 서버 재시작, 클라이언트 221B 재전송이 멈추는지 확인.
2. 멈추면 다음 단계: Bootstrap OpCode=2 응답 fragment (1400B급) 전송 구현.

## ACK SN/UNA 하드코딩 버그 수정 (2026-10-02 12:45, GPT 자문 반영)

### 증상
Window 수정(`1f 00`) 후에도 클라이언트가 221B 재전송 지속. ACK raw는 `52 00 1f 00`으로 정상이었음.

### 원인 (GPT 분석)
수신 221B의 KCP 헤더 `5100000146e2affa0100000000000000` 파싱:
`CMD=0x51, FRG=0, WND=256, TS, SN=1, UNA=0`.
서버는 ACK를 `SN=0, UNA=1`로 하드코딩 → 클라이언트가 보낸 SN=1을 ACK하지 않음.
관찰된 흐름과 일치: SN=0 1회 (우연히 ACK 일치) → 앱 재시도 SN=1 → SN=1 재전송 반복 (timestamp만 갱신).

### 수정 (`app/kcp/server_udp.py`)
- KCP 헤더 파싱 추가: `[CMD 1B][FRG 1B][WND 2B][TS 4B][SN 4B][UNA 4B]` (LE).
- 세션별 RX 상태 (`self.kcp_rx[session_id]["received"]`): 수신 SN 집합 유지.
- 중복 패킷 판별: 이미 받은 SN이면 복호화/앱 처리 생략, ACK만 전송 (KCP 규칙).
- 동적 ACK (`send_kcp_ack` 분리): `ACK SN = 수신 SN`, `UNA = 누적 확인` (가장 작은 미수신 SN).
  - 예: SN=1 수신 → ACK SN=1, UNA=2.
- ACK 전송 위치를 복호화 성공 path에서 패킷 수신 직후로 이동 (복호화 실패해도 ACK는 나감).

### 검증 방법
`git pull` → `python -m app.kcp.server_udp` → 로그에서 `KCP: ... SN=1` 수신 시 `ACK: ... SN=1, UNA=2` 나가는지, 이후 221B 재전송이 멈추는지 확인.

### 남은 것
- FRG 기반 reassembly (Bootstrap 응답 수신 대비).
- 서버→클라이언트 fragment 전송 (Bootstrap OpCode=2, SN=0 FRG=8 … SN=8 FRG=0).
- GPT 자문 원문: research/reports/2026-10-02-221B-ACK-SN-UNA-하드코딩-분석_GPT자문.md

## 동적 ACK 검증 + 앱 레벨 재시도 발견 (2026-10-02 12:43)

### 검증 결과
- `KCP: ... SN=2` 수신 → `ACK: SN=2, UNA=3` (동적 ACK 동작 ✓)
- SN=2 재전송 → `중복 패킷 (SN=2), 앱 처리 생략 — ACK만 전송` (중복 판별 ✓)
- SN=3 → ACK 3/4, SN=4 → ACK 4/5 (누적 UNA ✓)

### 새 발견: 전송 문제가 아니라 앱 응답 부재
SN=2,3,4가 각각 **동일한 172B 로그인 페이로드**(field 1=132193572)를 나르지만 **IV가 매번 다름**
(9accec13… → 24360360… → eaec6a82…). IV가 다르면 새로 암호화한 것이므로 KCP 재전송이 아니라
**앱 레벨 재시도**다. 즉 우리 ACK은 이제 받아들여지는데(클라이언트 SN 전진),
Bootstrap(OpCode=2) 응답이 없어서 게임이 로그인 요청을 반복하는 상태.

### S→C fragment envelope 실측 확정 (어플시작_로그인까지.json frame 177-187)
- Bootstrap 응답: 12개 fragment, sn=0..11, frg=11..0 (191-199는 재전송).
- fragment 구조: `[Session 8B][KCP 16B][ChunkLen 4B][chunk]`, chunk ≤1372B.
- chunk를 frg 내림차순으로 이으면 `[Flag 1B][IV 16B][Ciphertext]` (16256B, 16의 배수 ✓).
  - 즉 4B Length는 fragment별 chunk 길이. 메시지에 총 길이 필드는 없음.
- 단일 메시지는 `[Length 4B][Flag 1B][IV 16B][Ciphertext]` (frame 203: Length=209, Flag=0x84).
- 실측값: WND=32, UNA=1, 한 메시지의 TS 동일, 서버 SN 공간은 0부터 독립.

### 구현 (`app/kcp/server_udp.py`)
- `send_kcp_message(session_id, flag, plaintext, addr)`: AES 암호화 → 1372B chunk 분할 →
  KCP DATA fragment 전송. TX SN은 세션별 `kcp_tx`에서 0부터 증가. 자가 검증 통과
  (재조립→복호화 내용 일치, UNA/WND/FRG 실측값과 동일).
- `_current_rx_una()`: 0부터 세어 가장 작은 미수신 SN (gap 처리 포함).
- **Bootstrap probe** (실험용): 로그인 요청(OpCode=2) 수신 시 최소 protobuf
  (field 1=serial echo, field 2=2, 7B)를 flag 0x84로 암호화해 1개 fragment로 응답.
  목적: S→C 경로 전체(fragmentation→AES→클라이언트 파싱→재시도 중단 여부) 관측.
  OpInfo 실제 내용은 미확정이므로 일단 echo만.

## Probe 성공 — S→C 경로 완전 개통 (2026-10-02 12:52)

### 관측
- 새 세션에서 221B(SN=0) → ACK(SN=0,UNA=1) → 복호화 → probe 전송
  (`KCP DATA 전송: SN=0 FRG=0 chunk=33B`, serial=132671375 echo).
- **이후 221B 재전송 없음.** 클라이언트가 probe를 받아들이고 파싱했고,
  serial을 correlation해서 재시도를 멈춤.
- 즉 S→C 경로 전체가 동작: KCP fragment 조립 → AES-128-CBC 복호화 →
  protobuf 파싱 → NetworkCenter.TryHandleResponse → 재시도 중단.

### 화면이 전환되지 않는 이유
probe는 빈 OpInfo(serial+opcode echo만). `DataCenter.ProccessRequestRes`가
User/Chapters 등이 전부 null인 OpInfo를 받아서, 로그인 플로우가 다음으로 못 넘어가고
대기 상태에 머문다. 멈춘 게 아니라 **데이터를 기다리는 중**. 로딩바가 없는 것도 같은 이유.

### 남은 진짜 과제: OpInfo 응답 내용
- 응답 OpInfo의 protobuf **태그 번호**가 미확정. 필드 이름 45개는 GPT 런타임 분석에
  있으나(+0x88 User 등은 메모리 오프셋, protobuf 태그 아님) wire tag 매핑이 없음.
- 다음 실험: multi-tag probe (아래 별도 섹션).

## Multi-tag probe 실험 프로토콜 (2026-10-02 12:58)

### 배경
S→C 전송 경로는 개통됐으나(12:52 probe 성공) 화면이 전환되지 않음.
원인은 빈 OpInfo — 게임이 실데이터(User/Chapters 등)를 기다리며 대기.
병목은 응답 OpInfo의 protobuf 태그 번호 미확정.

### 목적
클라이언트 파서가 인식하는 태그 번호를 실험적으로 찾기.
Frida/Ghidra 없이 서버 로그 관측만으로 판정.

### 실험 설계
- probe 구성 (총 168B):
  - field 1 (varint): serial echo — correlation 유지 (재시도 중단의 조건)
  - field 2 (varint): opcode = 2
  - field 3~64 (nested, wiretype=2, len=0): 빈 메시지 56개
- 제외 태그: 4, 5, 12, 13, 14, 15 — 요청에서 문자열로 쓰는 태그라 wiretype 충돌 회피.
- 암호화 후: 168B → PKCS7 176B → [Flag 0x84][IV 16B][ct] = 193B → 1 fragment로 전송.

### 원리
protobuf 파서는 모르는 태그를 skip하고, 아는 태그는 내용이 비어도 객체를 생성한다.
따라서 실제 태그가 3~64 안에 있으면 해당 프로퍼티가 non-null이 되어
게임 로그인 플로우의 null 체크를 통과할 수 있다.

### 관측 포인트 (서버 로그 기준)
- **성공 신호**: probe 전송 후 클라이언트가 새로운 221B를 보냄
  (로그인 재시도가 아닌 다른 serial/opcode — 실측 PCAP frame 200의 168B C→S처럼).
- 실패 신호 1: 계속 대기 (아무 패킷도 안 옴) → 태그가 범위 밖이거나 빈 객체로는 부족.
- 실패 신호 2: 로그인 221B 재시도 재개 → 파싱 중 예외 발생 가능 (wiretype mismatch 등).

### 후속 분기
- 성공 시: 이진 탐색으로 최소 태그 집합 축소 (58개 → 절반씩 나눠서 재실험).
- 실패 시:
  - (a) 태그 범위 확장 (65~128)으로 재실험,
  - (b) 스칼라 필드용 varint=1 probe로 재실험,
  - (c) Frida로 `DataCenter.ProccessRequestRes` 수신 OpInfo의 프로퍼티 덤프.

### 구현 위치
- `app/kcp/server_udp.py`
  - `_pb_varint(field_no, value)`: varint 필드 인코더
  - `_pb_nested(field_no, payload)`: length-delimited 필드 인코더
  - `handle_kcp_data()` 내 probe 조립부 (opcode==2 && serial 있음)
  - `send_kcp_message(session_id, 0x84, probe, addr)`로 전송

## PCAP 대조 — 클라이언트의 서버-fragment ACK 패턴 (2026-10-02 13:00)

### 실측 (어플시작_로그인까지.json)
서버 fragment(177-187) 이후 클라이언트가 보낸 C→S 패킷 전부 파싱:
- frame 189 (84B) = **28B ACK 3개 번들**: (sn=1,una=3), (sn=0,una=3), (sn=2,una=3)
- frame 200 (168B) = 28B ACK 6개 번들 (sn=3,4,…, una=9)
- frame 201 (84B) = 28B ACK 3개 번들 (sn=9,11,…, una=12)
- frame 202 (168B) = 28B ACK 6개 번들, frame 204 (112B) = 28B ACK 4개 번들
- 즉 "168B 새 요청"으로 보였던 것들은 전부 **KCP ACK 번들**이었다. 애플리케이션 새 요청이 아님.
- 클라이언트 wnd: 253 → 247 → 256 (수신 버퍼에 따라 변동), una: 3 → 9 → 12 → 13 (수신 추적).

### 우리 테스트와 차이
- 실측: S→C fragment → C→S ACK 번들 (transport ACK은 항상 옴).
- 우리 (multi-tag probe): S→C 1 fragment (193B) → **C→S 아무것도 없음. transport ACK조차 없음.**
- 우리 서버는 모든 패킷 크기를 로그하므로(`handle_packet`), 로그에 없다는 건 실제로 안 온 것.

### 진단: multi-tag probe가 클라이언트 파서를 죽였을 가능성
- 12:52 단순 probe(field 1+2만, 둘 다 확인된 varint) 후에는 재시도 중단 = 파싱 정상.
- multi-tag probe는 field 3~64를 전부 wiretype=2(nested)로 전송.
- 그 중 실제 스키마에서 varint(스칼라)인 태그가 있으면 wiretype mismatch →
  protobuf 파서 예외 → 네트워크 스레드 사망 → ACK도 안 보내고, 재시도도 안 하고, 화면 로딩만 돔.
- 현재 정황과 완전히 일치: ACK 없음 + 재시도 없음 + 로딩 지속.
