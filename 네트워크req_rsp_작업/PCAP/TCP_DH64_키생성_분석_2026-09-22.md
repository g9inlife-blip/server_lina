# TCP DH64 키 생성 분석

- 분석일: 2026-09-22
- 대상: `Alioth.S1.Net.TCPTube$$TryOutput`
- 관련 클래스: `Alioth.S1.Common.DH64`
- 목적: TCP handshake 이후 실제 세션 Key가 생성되는 경로 확정

## 1. 결론

TCP의 DH 공유 비밀 계산과 16바이트 세션 Key 생성은 `TCPTube$$TryOutput`에서 실제로 수행된다.

`DH64$$Secret`의 호출자는 확인된 범위에서 다음 두 곳이다.

1. `Alioth.S1.Net.KCPTube$$Handshake2`
2. `Alioth.S1.Net.TCPTube$$TryOutput`

따라서 TCP는 별도의 `Handshake2` 함수가 없어도 `TryOutput` 내부에서 서버 DH 공개값을 읽고 공유 비밀을 계산한다.

## 2. TCP 클라이언트 DH 생성

앞서 확인한 `TCPTube$$Update`에서 연결 후 `DH64$$KeyPair`를 두 번 호출한다.

- `TCPTube + 0x48`: DH64 객체
- `TCPTube + 0x58`: client private #1
- `TCPTube + 0x60`: client private #2
- 첫 번째 public key와 두 번째 public key를 TCP handshake에 기록

DH 파라미터:

- modulus: `p = 2^64 - 59 = 0xFFFFFFFFFFFFFFC5`
- generator: `g = 5`
- `public = 5^private mod p`

## 3. TCP 서버 handshake 구조 확정

`TCPTube$$TryOutput`의 실제 코드에서 서버 응답을 다음과 같이 읽는다.

| Offset | Size | 의미 |
|---|---:|---|
| +0x00 | 8 | reserved / zero |
| +0x08 | 4 | length, 정상 handshake는 0x19 |
| +0x0C | 1 | marker = 1 |
| +0x0D | 8 | TCPConvID |
| +0x15 | 8 | server DH public #1 |
| +0x1D | 8 | server DH public #2 |

중요: 이전 PCAP 분석에서 +0x0D를 server DH public #1로 해석했던 내용은 실제 코드 기준으로 수정한다. 실제 코드는 +0x0D를 `set_TCPConvID`에 전달하고, +0x15와 +0x1D를 DH 공개값으로 사용한다.

## 4. 실제 Secret 계산

핵심 어셈블리 흐름:

```
+0x15 -> serverPublic1
+0x58 -> clientPrivate1
DH64::Secret(dh, clientPrivate1, serverPublic1)
    -> secret1

+0x1D -> serverPublic2
+0x60 -> clientPrivate2
DH64::Secret(dh, clientPrivate2, serverPublic2)
    -> secret2
```

수학적으로:

```
secret1 = serverPublic1 ^ clientPrivate1 mod p
secret2 = serverPublic2 ^ clientPrivate2 mod p
p = 2^64 - 59
```

여기서 `DH64$$Secret`는 내부적으로 `powmodp`를 사용하며, 호출 인자와 실제 코드 흐름으로 위 연산을 확정할 수 있다.

## 5. 16바이트 Key 구성

Secret 계산 직후 `BitConverter$$GetBytes`와 `Buffer$$BlockCopy`를 사용한다.

첫 번째:

```
BitConverter.GetBytes(secret1)
    -> Key[0:8]
```

두 번째:

```
BitConverter.GetBytes(secret2)
    -> Key[8:16]
```

따라서:

```
TCPTube.Key = LE64(secret1) || LE64(secret2)
```

즉 TCP 세션 Key는 총 16바이트이며, 각 64비트 Secret을 `BitConverter.GetBytes`로 변환한 결과를 순서대로 붙인다. Unity/ARM 환경의 현재 코드 경로에서 이는 Little Endian 바이트 배열로 해석한다.

## 6. State 전환

Key 생성이 끝나면:

```
TCPTube$$set_State(this, 3)
```

가 호출된다.

따라서 TCP handshake 처리의 상태 전환은 다음과 같다.

```
서버 handshake 수신
    -> TCPConvID 설정
    -> Secret #1 계산
    -> Secret #2 계산
    -> 16-byte Key 생성
    -> State = 3
    -> 암호화 TCP 통신 가능
```

## 7. PCAP 값과의 대응

기존 PCAP에서 확인한 TCP 서버 handshake 값:

- TCPConvID: `0x632`
- server DH public #1: `0xca4d30dba4429f27`
- server DH public #2: `0x7164b27b3d91d781`

따라서 당시 세션은 다음 계산 구조를 가진다.

```
secret1 = 0xca4d30dba4429f27 ^ clientPrivate1 mod p
secret2 = 0x7164b27b3d91d781 ^ clientPrivate2 mod p

Key = LE64(secret1) || LE64(secret2)
```

단, PCAP만으로 client private #1/#2를 직접 얻을 수 있는 것은 아니므로 현재 상태에서는 실제 16바이트 Key 값을 아직 산출하지 않는다.

## 8. 전체 TCP 흐름

```
TCP CONNECT
   |
   v
TCPTube::Update
   |
   +-- DH64::KeyPair #1 -> private +0x58 / public #1
   |
   +-- DH64::KeyPair #2 -> private +0x60 / public #2
   |
   v
Client handshake 송신
   |
   v
Server handshake 수신
   |
   +-- +0x0D TCPConvID
   +-- +0x15 server public #1
   +-- +0x1D server public #2
   |
   +-- DH64::Secret(private #1, server public #1)
   +-- DH64::Secret(private #2, server public #2)
   |
   v
TCPTube.Key = 16 bytes
   |
   v
State = 3
   |
   v
암호화 통신
```

## 9. 기존 암호화 분석과 연결

앞서 확인한 수신 경로는 다음과 같다.

```
TCP receive
 -> flags
 -> if 0x80: TCPTube.get_Key()
 -> Tools.DecryptUnSafe()
 -> clear 0x80
 -> if 0x40: DecompressUnSafe()
 -> clear 0x40
 -> ProtoBuf.Serializer.Deserialize<OpInfo>()
```

`Tools.DecryptUnSafe`의 유효 설정은 다음과 같이 확인되어 있다.

- RijndaelManaged
- BlockSize = 128 bit
- Key = 16 bytes
- Mode = CBC
- Padding = PKCS7
- 입력 구조: 16-byte IV + ciphertext

따라서 TCP DH 분석 결과와 기존 암호화 분석을 합치면:

```
DH handshake
 -> 16-byte TCPTube.Key
 -> AES/Rijndael-128 CBC/PKCS7
 -> OpInfo protobuf
```
